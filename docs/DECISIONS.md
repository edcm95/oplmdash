# Decisions (ADR) log

Format: context → decision → consequences. New decisions are appended at the end. A superseded decision is not deleted but marked `Superseded by ADR-XXXX`.

## ADR-0001 — Stack: Tauri 2 + Rust core + React/TS
*2026-10-22, accepted.*
- **Context.** Windows, Linux and macOS are needed, one core codebase for the GUI, CLI and server, and fast work with multi-gigabyte images (research/04).
- **Decision.** Tauri 2.12 + Cargo workspace + axum + clap + React 19/TS/Vite.
  - Only Rust has maintained libraries without C dependencies for CHD, reading and writing ISO, 7z, SMB2/3 and LZ4.
  - Builds are small, and there is an official CI (`tauri-action`) and an updater.
- **Rejected.**
  - Wails v3 (Go): still beta, no CHD, the SMB library is outdated. Reconsider after v3.0 is released.
  - Electron: a 120–200 MB installer, weak native libraries.
  - Avalonia, Flutter, Qt: the web UI for the server would have to be built separately.
- **Consequences.** A high barrier to entry into Rust. We keep the core synchronous, the linters strict, and many tests.

## ADR-0012 — Protecting the server API
*2026-10-22, accepted.* Refines ADR-0009.
- **Context.** A server on 127.0.0.1 without a token is reachable by any website open in the user's browser. A simple cross-site POST (form or `text/plain`) goes out without a CORS preflight, and DNS rebinding also allows reading responses. Starting from M2, the API will be able to change and delete files.
- **Decision.** For `/api/*`:
  - `POST /api/rpc` accepts only `Content-Type: application/json`. A cross-site request with that type requires a preflight, and we do not serve it.
  - If an `Origin` header arrives, it must match `Host`.
  - A loopback server **without a token** accepts only a loopback `Host` (`localhost`, `127.x.x.x`, `[::1]`). With a token this check is unnecessary: a token cannot be forged through DNS rebinding. That is why behind a reverse proxy the server may listen on 127.0.0.1.
  - The token is passed in `Authorization: Bearer`. Only the WebSocket `/api/events` allows `?token=`, because a browser cannot send headers during the handshake.
  - The UI receives the token once through the address `/?token=…`: it stores it in localStorage and removes it from the address bar.
  - The token is compared in constant time.
- **Consequences.**
  - A reverse proxy must pass the original `Host` (Caddy does this by default; in nginx you need `proxy_set_header Host $host`). Otherwise `Origin` will not match `Host`.
  - There is no API access from another origin. If needed, we will add an explicit allow-list.

## ADR-0013 — Formatting removable Media with error protection
*2026-10-22, accepted at the product owner's request. Replaces ADR-0008.*
- **Context.** The user needs to prepare Media from scratch: a USB stick or SD card for MX4SIO and the memory card emulator. A wrong filesystem, partition layout or cluster size is a frequent reason why OPL does not see games or is slow. The risks from ADR-0008 have not gone away: an error destroys data, and privilege elevation is different in each OS.
- **Decision.** Formatting is part of the product (SPEC DEV-3, DEV-4) with these restrictions:
  - Only removable drives on the USB or SD bus. The system and boot drive, as well as drives with a mounted OS, are not available at all.
  - Before the plan we show the model, serial number, size, current partitions and volume labels.
  - Confirmation by typing (for example the volume label or the drive size), not a single button.
  - Right before writing the drive is checked again by the same identifier: if it changed or was reconnected, the operation is cancelled.
  - The write is performed by a separate helper process with elevated privileges (`yaoplm helper --stdio`), not by the main process.
  - Parameters (filesystem, MBR/GPT, cluster, alignment) come from the Media and loader profile; the user may change them.
  - In automated tests we format only image files, never real drives.
- **Consequences.** This is the most dangerous operation in the product, so its code is reviewed separately by the owner and tested on his Media. The milestone is v0.2: until then there is only read-only Media diagnostics (DEV-2).
- **Refinement from research/06 (2026-10-22).**
  - Disk access: elevated privileges are needed only on Windows (helper through UAC and a protected named pipe). On Linux the unprivileged helper obtains the device handle through udisks2 (one polkit request); on macOS through `authopen` (a prototype is needed). In server mode and in Docker there is no formatting.
  - Confirmation by typing is the drive size.
  - We write the filesystem first and the partition table last; we check disk identity through the same handle we write with.
  - Only drives with a 512-byte logical sector: FatFs in OPL is built with `FF_MAX_SS 512` (verified in `fjtrujy/FatFs`, branch `iop-r0.16`).
  - The choice of engine (our own exFAT or the system one on Windows and macOS) depends on the exFAT patent question — SPEC, open question 6.

## ADR-0014 — Installing loaders only from official releases
*2026-10-22, accepted.* Supplements ADR-0007.
- **Context.** The owner wants to install different builds from the program: official OPL, RiptOPL, the MMCE fork and others (SPEC LDR-1…5). PS2 program binaries change often and have different licences.
- **Decision.**
  - We download only from official project releases (GitHub Releases and similar), on an explicit user action. Loader binaries are not bundled into YAOPLM.
  - A build is fixed by the asset's SHA-256, not by the tag: "floating" tags such as `latest` are overwritten in place. We take the hash from the GitHub API if the release publishes it; otherwise we compute and show our own. We cache it and show the licence and a link to the sources.
  - We do not write launch-method configs (FreeMcBoot, PS2BBL); we show the user the lines for them (SPEC BOOT-1).
  - The user can install from their own archive without a network.
  - We do not install exploits (FreeMcBoot, PS2BBL) onto a physical memory card.
- **Consequences.** The loader catalogue is data that is updated without a new program release. When a project's release format changes, it is enough to fix its entry in the catalogue.

## ADR-0015 — Reference projects as a source of edge cases
*2026-10-22, accepted.*
- **Context.** The source code of OPL, its forks and neighbouring programs accumulated years of fixes for special cases, hardware bugs and firmware quirks. Many of them are described nowhere except code comments, commits and issues. Searching for them on forums takes a long time.
- **Decision.**
  - We keep a repository index in `docs/research/REFERENCES.md` and local clones in `D:\yaoplm-testdata\refs\<owner>__<repo>`.
  - Before implementing a format or a device feature, we read the matching code in upstream OPL and the forks, their commits and issues; if needed, forum threads (psx-place is read through the user's Chrome).
  - We compare implementations. The reference for behaviour is upstream OPL (CLAUDE.md: "Follow OPL source"); forks and other managers are a source of edge cases and fixes that we verify before porting. In a comment to our code we cite the source file and commit.
  - Licences: OPL code (AFL-3.0) and ps2sdk (AFL-2.0) are not copied but reimplemented from the logic (ADR-0002). Code under GPL-3-compatible licences may be ported with attribution.
- **Consequences.** The index must be kept current (`git pull` on the clones), and findings must be recorded in research/.

## ADR-0016 — Our own ISO9660 reader and fixture generator instead of hadris-iso
*2026-10-22, accepted in M1.* Refines the stack in ARCHITECTURE.md §2.
- **Context.** The game ID must match what OPL shows (IMP-2). isofs in OPL is much stricter than the standard: it reads only sector 16, looks in the root for exactly `SYSTEM.CNF;1` via `strcmp` (case-sensitive, version `;1` and the filler byte), and handles zero-length records its own way (research/08 §3). A general-purpose library finds the file where OPL does not see it and hides the reason from us. Tests need "wrong" images (without `;1`, with a lowercase name, with a second PVD for DVD-9, larger than 4 GiB with no room on the disc), and standard writers do not produce them.
- **Decision.**
  - `yaoplm-formats::iso9660` — our own minimal reader replicating the OPL isofs logic (PVD, root lookup, file read, DVD-9 layer probe), plus a simple standard directory listing for display.
  - `yaoplm-test-support::iso` — our own ISO9660 generator (PVD, terminator, path tables, directories, files) that streams the image through `Read + Seek`.
  - We do not adopt `hadris-iso` for now. We will return to it if full ISO writing is needed (for example BIN/CUE → ISO in IMP-1 can be done without it: it is copying data sectors).
- **Consequences.** About 600 lines of our own code, but every rule is covered by a test and a fuzz target. The ZSO reader is integrated into the same `SectorSource` interface, so all checks work the same for ISO, ZSO and a chain of `ul` chunks.

## ADR-0017 — Milestone branches are merged with a regular merge commit
*2026-10-22, accepted at the product owner's suggestion.*
- **Context.** Milestone PRs (M0, M1…) contain dozens of meaningful commits with requirement IDs. With squash the history collapses into one commit: `git blame` for a specific rule and `git bisect` down to a commit are lost.
- **Decision.** Milestone and large-task PRs are merged via "Create a merge commit". Small PRs with one logical change (for example docs only) may be squashed.
- **Consequences.** Every commit in the branch must build and pass tests on its own. The agent merges small fixes ("fix typo", clippy edits) into the original commits before opening the PR (`git commit --fixup` + `git rebase --autosquash`). A short per-PR history is given by `git log --first-parent main`.

## ADR-0018 — Our own OPL fork to fix found bugs
*2026-10-22, accepted by product owner's decision.*
- **Context.** In M1 we found OPL bugs on "wrong" input data (research/08 §10). Three of them are fixed neither in upstream nor in any fork: a cheat with an empty name from an indented comment, a hang when writing an ISO directory with an empty name, and a division by zero in ZSO when `align > 11`. Another five are fixed only in RiptOPL. Upstream develops slowly, although it accepts community PRs.
- **Decision.**
  - A fork of `ps2homebrew/Open-PS2-Loader` under the owner's account, a separate repository. The fork licence is AFL-3.0, like OPL. We do not copy YAOPLM code (GPL-3) into the fork, nor fork code into YAOPLM (ADR-0002).
  - Our own line of development: we commit fixes directly to the fork rather than preparing them as upstream PRs. We periodically pull upstream changes into the fork. Sending individual fixes upstream is possible but not mandatory, and only with the owner's approval.
  - Automatic build in the fork's GitHub Actions on every push to the main branch, publishing the ready ELF (following the upstream rolling `latest` release), so the owner can put our OPL with fixes on the console.
  - We port RiptOPL fixes selectively: only real bugs and only after a "before/after" check on reproducing input data. We state the authorship (the same AFL-3.0 licence).
  - Testing is on the owner's console and on the `yaoplm-test-support` Fixtures; purely logical functions (CHT parsing, `SYSTEM.CNF`, `ul.cfg`) are additionally checked by building them on a PC in a test harness.
  - As soon as the fork starts publishing builds, we will add a loader profile for it to YAOPLM (the format rules still match upstream for now).
- **Consequences.** A second repository with its own cycle appears, and so does the duty to pull upstream. YAOPLM still does not rely on the fixes: the manager does not create "wrong" data and warns about it during scanning, because users may have any loader installed.

## ADR-0019 — Volumes and preallocation through the OS API, `unsafe` in only one module
*2026-10-22, accepted in M2.* Refines the stack in ARCHITECTURE.md §2 and §8.
- **Context.** For DEV-1/DEV-2 and for re-checking Media before writing, we need the volume serial number, cluster and sector size, bus (USB/SD), partition table and partition offset, and for writing (IMP-7) — space preallocation. `sysinfo` gives only the mount point, filesystem type, capacity and a "removable" flag (on Windows that is `GetDriveTypeW`, and USB drives there are "fixed"), does not see network drives and cannot do "volume by path". None of the crates we found covers everything at once.
- **Decision.**
  - `yaoplm-device` talks to the OS directly:
    - Windows — `windows-sys` 0.61: `GetVolumeInformationW`, `GetDiskFreeSpace(Ex)W`, `GetVolumePathNameW`, `IOCTL_STORAGE_QUERY_PROPERTY` and `IOCTL_DISK_GET_PARTITION_INFO_EX` on a volume handle with access 0 (without administrator rights); preallocation — `SetFileInformationByHandle(FileAllocationInfo)`;
    - Linux — `/proc/self/mountinfo`, sysfs, `/dev/disk/by-uuid` and `by-label`, `statvfs` and `fallocate(FALLOC_FL_KEEP_SIZE)` through `rustix` 1.1;
    - macOS — `statfs` through `rustix` and `/Volumes`; the bus, partition and serial number are not detected yet, and there is no preallocation (`F_PREALLOCATE` in rustix also lengthens the file, and msdosfs fills the extension with zeros).
  - We do not adopt `sysinfo`.
  - `unsafe` in the workspace is still forbidden (`unsafe_code = "deny"`). The only exception is `crates/yaoplm-device/src/sys/windows.rs`: thin wrappers over documented Win32 calls, Rust allocates the buffers, and each block has a `SAFETY` comment. *Refinement ADR-0037:* `sys/fiemap.rs` (Linux) and `sys/log2phys.rs` (macOS) are arranged the same way for counting file fragments.
- **Consequences.** About 300 lines of platform code that CI checks on three OSes. Details for macOS (DiskArbitration or `diskutil`) come later, together with DEV-3.

## ADR-0020 — Renaming changes what OPL associates with the title; VMC is never touched
*2026-10-23, accepted in M2.* Refines SPEC GAME-1 and GAME-2.
- **Context.** GAME-1 required "synchronously updating ART, CFG, CHT and VMC references" on renaming. But OPL names CFG, ART and CHT by game ID, not by title, and neither OPL nor its forks nor neighbouring managers touch them when the title changes (research/09 §4). By default OPL names VMC cards `<group ID or ID>_<slot>`; there are also `generic_0`/`generic_1`: one card is often shared across a game series.
- **Decision.**
  - The new title changes only the image name or, for `ul`, the chunk names (their hash is computed from the title) and the `ul.cfg` record; `games.bin` in the folder is deleted.
  - CFG (and wOPL `.info`), `ART/<ID>_*` and `CHT/<ID>.cht` are moved only when the effective ID changes: the user fixed the ID in an old-format name or in the `ul.cfg` record, or a name-format change alters the ID OPL will take. If the old ID still belongs to another game, the files are copied rather than moved. An existing file with the new name stops the plan.
  - VMC files and the values of `$VMC_0`/`$VMC_1` never change: CFG moves as a whole and keeps pointing at the same card. Thus "VMC references" are preserved and shared cards are not broken.
  - By default deletion erases only the image (or the `ul.cfg` record and chunks). CFG, covers and cheats — only on explicit choice and only if the ID is not used by another game; VMC is never deleted.
  - Every CFG is copied to `.yaoplm/backup/<id>/` before being moved or deleted (CFG-5).
- **Consequences.** Renaming cannot damage another game's settings. Deleting VMC saves is a separate feature with separate confirmation (VMC-2, later).

## ADR-0021 — Transactions with a commit point and a journal on the device
*2026-10-23, accepted in M2.* Refines ARCHITECTURE.md §5.
- **Context.** SPEC requires atomic writing and a journal for multi-step operations with rollback or roll-forward. A USB stick can be pulled out in the middle of slicing an 8 GB file; none of the managers we studied survives such a failure without leaving garbage on the Media (research/09 §1, §5).
- **Decision.**
  - A plan is a list of transactions (one game, one rename…); a transaction is a list of steps with a commit point. Steps before it are reversible. The step right before it makes the change visible to OPL: renaming the image into place or writing `ul.cfg`. Steps after it only finish the work: deleting `games.bin`, deleting at the user's request, deleting the source on a move.
  - The journal is JSON in `.yaoplm/journal/<id>.json` at the device root: the whole plan and the number of completed steps of each transaction. It is overwritten atomically after each step and deleted when the plan is complete. OPL does not show the root; NHDDL skips names with a dot.
  - A failure or cancellation before the commit point rolls the transaction back (newest steps first); after it the journal remains and recovery rolls the transaction forward. An uncommitted transaction may, at the user's choice, be repeated instead of rolled back. Recovery steps are idempotent, so an interrupted recovery can be run again.
  - Before the first write the executor re-checks the volume fingerprint (serial number, filesystem, size, label), that the sources are unchanged (size and modification time), free space and the absence of unfinished journals.
  - Plans are stored on the core side (`PlanStore`); the client sends only the plan id. A plan runs once and lives for an hour. A plan that deletes user files requires an explicit `confirmDelete`.
  - Write jobs run strictly one at a time in queue order: parallel writing to one USB stick fragments both games.
- **Consequences.** A `.yaoplm` folder appears on the Media (journals and CFG backups). A package of N games is N independent transactions: a failure on the third game leaves the first two in place.

## ADR-0022 — Loader catalogue, build identity by hash, and updates only within a channel
*2026-10-23, accepted at the product owner's request.* Refines ADR-0014 and ADR-0018; details — SPEC §5.10.1, sources — research/07.
- **Context.** The owner wants a mode for installing a loader onto Media (folders by profile plus the ELF by launch method) and updates: the program determines which loader and which version is on the USB stick and offers a fresh build of the same fork, not another one. Difficulties: the ELF is packed with ps2-packer and the version inside is not visible; floating tags (`latest`, `rolling`) overwrite assets; GitHub `digest` exists only for recently uploaded files; of the repositories we control only our own YAOPLM fork.
- **Decision.**
  - The build catalogue is data in `data/loaders/`, not code: family, channel, repository, licence, profile, assets, folder set, path presets, fingerprints. It is updated without a new program release.
  - Build identity is family + channel + version + SHA-256 of the ELF. Hash history is append-only: for YAOPL — `HASHES.txt`, appended by the fork's CI; for third-party repositories — `data/loader-hashes/<id>.txt` on our side, topped up once a day by a scheduled workflow from the GitHub Releases API; everything YAOPLM downloads itself is remembered in a local cache. An unknown hash is a normal case: such a build is shown as "family X, version unknown".
  - Recognition order: install manifest `.yaoplm/manifest.json` → hash history → `title.cfg` → file names → fingerprints of settings files. The result always comes with a confidence level.
  - An update is offered only within the same family and channel; changing the fork, channel or ELF path is a separate explicit "Replace" action. An update changes only the ELF (and the application package for RiptOPL), keeps a backup of the previous ELF and can roll back.
  - Installation writes only to the selected Media: folders, the ELF (temp + rename), the manifest, startup settings optionally and preserving foreign keys. The memory card and launcher configs are not touched (BOOT-1): we show the lines for FreeMcBoot and PS2BBL.
  - Network only on a user action or on the daily check enabled in settings; before downloading we show the licence and authors; binaries are not bundled (ADR-0007, ADR-0014).
  - Every connected Media has a card, but installation, update and replacement are offered only to Media that suit the loader: the system drive, a read-only volume and any Media with a "Not suitable for OPL" verdict get no buttons, and no automatic update window is shown for them. "Install…" on a USB stick with foreign files offers to format it only through DEV-3 with the ADR-0013 protections (v0.2); before that — add OPL next to the files or format manually. The automatic "Update available" window appears when Media is connected, from the catalogue cache, without network, once per "Media, installed build" pair; "Not now" is remembered, and the button on the card opens the window again. The setting "Automatically offer loader updates" (enabled by default) disables the window entirely, both at startup and when Media appears; the buttons on the card remain.
  - POPStarter and Ember come only inside the RiptOPL package from its author's release (POPStarter unchanged as part of the package, Ember under its own licence with a licence file and a link to Gageformer); they are not downloaded or bundled separately. Sony files (`POPS.ELF`, `IOPRP252.IMG`, BIOS) — never. The device card shows the state of these components and the exact paths of missing files and does not paraphrase instructions: the catalogue stores links to each build's official documentation (upstream README and wiki, the RiptOPL docs site, POPSTARTERINFO), and the UI leads to them (PS1-1).
  - YAOPL uses the OPL 1.2.0 beta profile: the format rules match, and the fork's fixes concern only what the loader tolerates. If the formats diverge, we will split the profile in a separate ADR.
- **Consequences.** The repository gains a catalogue and a hash history as versioned data, plus a scheduled workflow (CI minutes: one run a day on Linux, ADR-0011). The YAOPLM fork's CI must publish `HASHES.txt` (a task in the fork repository). LDR-1…LDR-4 for OPL and YAOPL are done in M5 (v0.2) together with formatting and the preparation wizard (DEV-3, DEV-4); forks — in M6; M4 stays with covers, metadata and the release build so as not to overload the milestone.

## ADR-0023 — The loader profile is determined by the Media; the setting sets the default and override
*2026-10-23, accepted at the product owner's request.* Refines LIB-1 and ADR-0022; rules — SPEC §5.1.1.
- **Context.** Before M3 the profile was a single global setting (OPL 1.2.0 beta by default) passed into every request. The owner has several Media for different loaders, and a global choice is easy to forget to switch: then ZSO and JPG rules of the wrong version would land on a USB stick running OPL 1.1.0.
- **Decision.** The profile is computed for each Media from its files, without network: installed loader (manifest, hash) → settings files and their keys → indirect signs (exFAT, ZSO) → default from settings. The `InspectDevice` response carries the profile, the confidence level and the reason. The "Loader profile" setting gets "Auto (by Media)" as the default; an explicit choice remains an override and can be remembered for Media by volume serial number. The UI always shows the effective profile and why it is so. Scanning and plans receive the effective profile; the core itself guesses nothing.
- *Refinement ADR-0040:* there is no global profile setting any more; the choice for Media and detection by its files apply.
- **Consequences.** A wrong detection is fixed with one override per Media; unknown Media behaves as before (the default). The signs match LDR-4, so both tasks are done together in M5.

## ADR-0024 — Built-in title database: compressed JSON inside the binary
*2026-10-23, accepted in M4.* Refines ARCHITECTURE.md §6–§7 and SPEC META-1.
- **Context.** We need a database "serial number → title, region, related serials, Redump names" from PCSX2 `GameIndex.yaml` (GPL-3.0) and the libretro-database PS2 DAT (CC BY-SA 4.0). Redump names are also needed for libretro-thumbnails: the files there are named by Redump. Options: an SQLite file next to the binary or compressed JSON inside it.
- **Decision.** `scripts/build-data.py` builds `data/titles.json.gz` (12 978 serials, 377 KB, gzip with zero mtime: the same input gives the same bytes) and `data/ATTRIBUTION.md` from `data/attribution.json` with SHA-256 of the input files. `yaoplm-core::titles` embeds the file via `include_bytes!` and parses it on first access (`OnceLock`, a few milliseconds, about 3 MB in memory). IDs are accepted in both spellings (`SLUS_200.62`, `SLUS-20062`, region suffixes discarded; `yaoplm_formats::serial`). For Japanese titles `name-en` is preferred.
- **Rejected.** SQLite: pulls C compilation into the core, needs a file on disk next to each of the three front ends (and in Docker), and we have no queries more complex than "find by key". Downloading the database from the network on first launch: contradicts the offline-first approach and ADR-0007.
- **Consequences.** Updating the database means rebuilding with the script and committing (`python scripts/build-data.py`); the file is marked `binary` in `.gitattributes`. The derived database remains under CC BY-SA 4.0 for the libretro part and is distributed with the program under GPL-3.0-or-later.

## ADR-0025 — Covers: search as a job, write as a plan, backup by move
*2026-10-23, accepted in M4.* Refines ARCHITECTURE.md §5–§7, SPEC ART-1…ART-4, ADR-0021.
- **Context.** Mass cover downloading for hundreds of games takes minutes (no more than one request per second per source, ADR-0007), and a synchronous plan request cannot bear that: no progress, no cancellation. At the same time writing to Media must remain a plan with confirmation (rule 1). An existing cover cannot simply be deleted on replacement: deleting user files requires separate confirmation, and the journal must not carry image bytes.
- **Decision.**
  - `FetchArt` is a job: it scans the Media, for each game in scope (`missing` by default or `all`) queries `yaoplm-net`, writes a journal line per game (found, from cache, not found, error) and finishes with a `PlanKind::Art` plan that the user confirms like any other. `SetArt` (file, drag-and-drop, clipboard) and `DeleteArt` return a plan immediately.
  - Sources: xlenore/ps2-covers by serial, then libretro-thumbnails by Redump name from the built-in database (ADR-0024), first `thumbnails.libretro.com`, then raw GitHub. No GitHub API. Every source has a local-mirror mode (a folder with the repository layout), which also serves as a mock for tests and e2e. Source and mirror settings come with the request from the UI; on the server the mirror must lie inside the allowed roots.
  - Cache: `art-cache/<source>/<key>/original.<ext>` plus derived `COV-<w>x<h>.png`, a `cache.sqlite` manifest; "not found" is remembered for seven days; `ETag`/`Last-Modified` for conditional requests; the data directory is `YAOPLM_DATA_DIR` or the system application folder (`--data-dir` on the server). The cache can be deleted without loss.
  - Re-encoding: any PNG/JPEG/BMP/GIF/WebP → PNG 8 bits per channel, COV size from the profile (140×200 for OPL, 280×400 for RiptOPL), stretch without cropping, as OPL itself does (ADR-0005).
  - Write plan: one transaction per game, the source of the `WriteFile` step is a file in the host cache, so the journal stores only the path. An existing `ART/<ID>_COV.*` file is moved (`Rename`) to `.yaoplm/backup/<id>/ART/` before the commit point: a rollback returns it to its place, there is no deletion. `DeleteArt` copies the file there too and deletes it after the commit point, which requires `confirmDelete`.
  - Display: on the desktop through the Tauri asset protocol with permission only to `<root>/ART` at runtime; on the server `GET /media/art?path=` only for files `ART/<ID>_<SUFFIX>.png|jpg|bmp` inside the roots, with `ETag` and `?token=` like the event stream.
- **Consequences.** In M4 only COV; the other types (ICO, SCR, BG…) are added as new `ArtKind`s in the same pipeline (v0.2). The network is used only inside `FetchArt`, on a user action. A `.yaoplm/backup/<id>/ART/` folder appears on the Media after a cover is replaced or deleted.
- **Refinement (2026-10-23, by product owner's decision).** The split "import, then a separate button" is temporary. In v0.2 cover search is built into import (SPEC ART-8, §5.4.1): a checkbox on the add screen runs the same `FetchArt` job for the IDs of the images in the plan, and the import plan is rebuilt with its result, so the image and the cover are written by one confirmed plan. The pipeline itself (a job with a journal → a plan with files from the cache → a backup by move) does not change; only the import plan now accepts ready-made covers. A cover never blocks an import. The separate "Download covers" button remains for already imported games. Editing by type (COV, ICO, COV2, BG, SCR, SCR2, LGO, LAB) in the game card is part of ART-2/ART-3 in v0.2.

## ADR-0026 — Dump verification: Redump DAT on demand, its own weekly limit, verdicts from the hash cache
*2026-10-23, accepted in M5.* Refines SPEC GAME-5 and META-2, ARCHITECTURE.md §6.
- **Context.** `https://redump.info/datfile/ps2/serial,version` serves a zip with one Logiqx DAT (about 1.3 MB, 11 845 games as of 2026-10-23), but without `ETag` and `Last-Modified`: the conditional requests from META-2 save nothing. Redump computes CD hashes over raw BIN tracks (2352 bytes per sector), so an ISO ripped from a CD will never match. Reading a 4 GB image from a USB stick takes minutes, and the library is scanned constantly.
- **Decision.**
  - The DAT is stored in the application data directory (`db/redump-ps2.dat`, metadata `db/redump-ps2.json`). Redump is queried only via the "Download" or "Check for update" button and no more than once a week; any server response counts, including an error page (`db/redump-ps2.asked`); a missing response (no network) does not count. Updates and import happen one at a time. Instead of downloading, the user can import a manually downloaded `.dat` or `.zip` without a network. Files are written through a temporary file, `fsync` and rename; corrupted metadata is restored from the DAT, and an unreadable DAT is treated as absent.
  - CRC-32 and SHA-1 hashes (MD5 optionally) are computed in one read of the image: ISO as is, ZSO decompressed, `ul` stitched together from its parts. A match is by SHA-1 and size; with several matches the record with the game ID wins.
  - Statuses: "verified", "bad dump" (the ID is in Redump but there are no hashes), "unknown" with a reason (no DAT; not in Redump; a CD image — with records of the same ID and a "same size" hint), "verification error" (the image is unreadable).
  - Hashes are cached in `cache.sqlite` keyed by "volume (serial number, filesystem, size) + path + size + modification time" of each file. Scanning shows a verdict only from the cache (it opens it read-only and creates nothing), against the current DAT. The "Re-read from scratch" option (`fresh`) ignores the cache.
- **Consequences.** Verification never writes to the Media. A new DAT changes verdicts without re-reading images. ISOs from CDs get "unknown: CD image" instead of a false "bad dump". Without a DAT, verification still computes and caches hashes.

## ADR-0027 — ISO ↔ ZSO ↔ ul conversions and a refinement of recovery
*2026-10-23, accepted in M5.* Refines SPEC GAME-4 and ADR-0021.
- **Context.** Conversion deletes the source image, and free space on a USB stick is often tight. The ZSO size is unknown in advance. `ul.cfg` records with the same title and ID point at the same parts (part names are the CRC of the title and ID, `sbCreatePath_name()`), and on deletion OPL (`sbDelete()`) removes only one record. Review found that an interrupted recovery with a step that fails every time (a ZSO larger than 4 GB on FAT32) would repeat forever.
- **Decision.**
  - One transaction per game in all directions (ISO, ZSO, ul either way). The new form is written next to the old one; the old one is deleted after the commit point and only with `confirmDelete`. The game ID does not change: CFG, images, cheats and VMC keep working. If with "title only" names the ID in `ul.cfg` differs from SYSTEM.CNF, the ID stays in the file name.
  - Space is counted by peak (the new file before the old one is deleted); ZSO — by worst case, rounded up to a cluster per file.
  - All records of this game are removed from `ul.cfg` (a departure from `sbDelete()`, research/12 §3). Parts whose size OPL would read differently (all but the last, exactly 1 GiB) are not stitched together.
  - Rollback and roll-forward of a ZSO step touch the file only if its header says it is a ZSO of this source.
  - Refinement ADR-0021: recovery transactions keep the original commit point (the uncommitted part remains reversible), and a recovery plan after rolling back one transaction continues the rest and closes the journals. A step that cannot execute is rolled back once, not repeated on every recovery.
- **Consequences.** On FAT32, converting an almost 4 GB image to ZSO may roll back if the ZSO turns out larger than 4 GB (the plan warns). After a failed "Continue" in recovery the game stays as it was.

## ADR-0028 — Sources in archives, CHD and multi-track BIN/CUE
*2026-10-23, accepted in M5.* Refines SPEC IMP-1b.
- **Context.** Games are often downloaded as zip and 7z. Extracting to a temporary folder (as Orbit does) doubles space and time. CHD stores a block map at the end of the file, and the blocks refer backwards. PS2 discs with CD audio after the data track exist, but OPL runs only single-track discs. The RAR decoder (`unrar`) is licence-incompatible with GPL-3.
- **Decision.**
  - A zip or 7z archive is read like a folder (`ArchiveSources`); the image is decompressed on the fly and written straight to the Media, without temporary files. Archive member names are sanitised as 7-Zip does (no drive letters, `.` and `..`), so an archive member cannot escape the archive. The CRC of each member is checked when read to the end.
  - Archives are never deleted, even in move mode (the plan says so). An archive inside an archive is not opened. A CHD inside an archive is not read (it must be extracted first). Password-protected archives are rejected. RAR remains in IMP-1c behind a separate build option.
  - CHD: DVD and CD (`CHT2`), saved pregap, all data modes; a CHD that needs a parent CHD is rejected immediately.
  - BIN/CUE: data is track 1. Audio tracks after it are discarded with a warning. A second data track or a second session is rejected. Both Redump files, one per track, and a single BIN with all tracks are supported.
- **Consequences.** Importing from a solid 7z with several games decodes everything before the needed game. Music from CD audio in such games does not play on PS2, just as with any recording for OPL.

## ADR-0029 — Core texts are phrases: catalogue key and parameters
*2026-10-23, accepted in M5.* Refines docs/I18N.md and ARCHITECTURE.md §4.
- **Context.** The UI is English-only, but the core assembled plan, transaction and job headers and error texts as English strings (`format!`), while the UI catalogue also holds English text; keeping English templates in both Rust and the UI catalogue would eventually diverge.
- **Decision.**
  - The type `Phrase { key, params }` in `yaoplm-core`: a catalogue key (`titles.*`, `errors.*`, `notices.*`) and named parameters. A parameter is a number (the quantity selects the plural form; a size in bytes is written as `{{size, bytes}}`), text (name, path, ID, format) or a nested phrase.
  - The core takes English text from the same catalogue `web/src/locales/en/translation.json`: it is embedded via `include_str!`, like `data/titles.json.gz` (ADR-0024). The CLI, logs and English UI say the same thing. A key missing from the catalogue is an error in a debug build.
  - Alongside the phrase and English text go plan and transaction headers (`title_phrase`), job headers and the current item, plan execution errors (`ExecError::phrase`), planning errors (`OpError` stores a phrase) and API errors (`ApiError.phrase`). Journals on the Media get a `title_phrase` field with `serde(default)`: old journals are readable, their headers remain English (the `titles.plan` key passes the text as is).
  - The UI translates the phrase itself (`phraseText`, `errorText` in `web/src/lib/phrase.ts`): nested phrases first; a key missing from the catalogue (the core is newer than the UI) shows the core's English text.
  - Checks: vitest finds phrase keys in the core and API sources and requires a translation for every supported language, and also rejects `titles.*`/`errors.*` keys the core does not use; core and API tests compare the English text with the phrase.
- **Rejected.** English templates in both Rust and the catalogue (they will diverge). Translation on the core side: the core does not know the UI language, and the server serves different clients. gettext or Fluent: a second catalogue format next to i18next.
- **Consequences.** New user-facing text in the core is a phrase and a key in every supported language in the same commit.
- **Refinement (2026-10-23, second step).** Plan notices, game warnings, Media advice and skip reasons (`notices.*`) also became phrases, and reasons from format parsers — `reasons.*`, fragments for embedding after a colon. The `Phrase` type and the English renderer were moved to the `yaoplm-i18n` crate so that `yaoplm-device` can use them too; `yaoplm-core` re-exports them. `Notice` stores the phrase (in a `Box`, next to the code and the English `message`); a blocked plan embeds the phrase of the blocking notice in full, with sizes. Several codes were split so that each has one text (`allHaveCovers`, `sourceMissing`, `tooLargeUseUl`, `imageDeletedAfterUl`, `chunksDeletedAfterImage`, `relatedShared`, `zsoDecompressedForOpl110`/`ForUl`). Numbers in the UI are formatted by language ("5.0 GiB"). The translation boundary is docs/I18N.md, rule 8.

## ADR-0030 — Dump verification on add: hashes in the same pass, raw CD track, verdict order
*2026-10-23, accepted in M5.* Refines SPEC GAME-5 and ADR-0026.
- **Context.** The product owner decided that games are verified on add by themselves (enabled by default). A separate read of the USB stick after writing is the slowest part: writing a 4 GB image and reading it again doubles the time. Redump hashes CDs over raw BIN tracks (2352 bytes per sector), while ISO (2048 bytes) is written to the Media, so a "confirmed" verdict for a CD is possible only if the raw data track is hashed already at the source.
- **Decision.**
  - Hashes are computed in the same stream as the write (`yaoplm-core::checks`): CRC-32 on the write stream, SHA-1 and MD5 in worker threads (`StreamHasher`). The image is hashed as OPL reads it: ISO sectors; a ZSO copied as is is decompressed on the fly (`zso::StreamDecoder`); when writing to ZSO, the ISO data is hashed before compression.
  - For a CD from BIN/CUE and CHD the raw data track is additionally hashed (`SectorSource::raw_sector`), sector by sector as it is decoded. Audio tracks in the DAT are shared between discs, so only the data track (the game's first `.bin`) is matched by raw hash.
  - Hashes are emitted only if the source ran through completely from the first byte in one pass. A resumed or failed write produces no hashes; such a game is verified by the regular `VerifyGames`.
  - After writing, the hashes are put into the cache keyed by the new file on the Media (volume, path, size, mtime), as `VerifyGames` would do, and the track hash goes into the `tracks` table keyed by "SHA-1 and image size". Library scanning takes the verdict from the cache and finds the track through that link, so a CD keeps "confirmed by track" after a rescan.
  - Such cache rows are marked as taken during writing (`hashes.from_writing`): the hashes come from the source bytes, and the Media is not re-read after writing; otherwise a USB stick with a fake capacity or with failures that corrupted the data would get "confirmed (from cache)" without a single read. Library scanning shows the verdict for marked rows too, while an explicit dump check (`VerifyGames`) treats such a row as a miss: it reads the files from the Media once and stores a regular row. Cache rows from before this mark are treated as read from the Media.
  - Verdict order: raw track confirmed → by track; otherwise ISO confirmed → by image; otherwise the track verdict (it is more accurate for CDs). `DumpCheck.byTrack` shows what the verdict was based on.
  - The "Verify dumps on add" toggle on the add screen (enabled by default, `PlanImport.verify`; since ADR-0034 it is not in settings); in the CLI verification also runs by default, and `yaoplm add --no-verify` turns it off. Without a DAT the hashes are still stored: the verdict appears once the DAT is downloaded.
- **Consequences.** Verification on add does not re-read the Media and barely slows the write (SHA-1 in a separate thread; `opt-level = 3` for `sha1`, `md-5` and `crc32fast` in the dev profile so that debug builds are not slow). On FAT32 a daylight-saving change shifts the mtime and the cache key; the CD verdict is then restored by re-hashing and the link in `tracks`. Risk: Mode 2 Form 2 sectors in the pregap of real CDs; a check against a real Redump dump is needed (research/13 §6).

## ADR-0031 — Covers and titles when adding games: a set of covers instead of a plan
*2026-10-23, accepted in M5.* Refines SPEC ART-8 (§5.4.1), META-1 and the ADR-0025 refinement.
- **Context.** Covers must land together with games on one confirmation, while the search takes minutes and may find nothing. If the search returned a plan, it would have to be merged with the import plan. The product owner also asked to substitute the title from the database when the ID is known, so that adding is as simple as possible.
- **Decision.**
  - `FetchArt` with `import: <import plan id>` searches covers for the IDs in that plan (each ID once, skipping those that already have a cover on the Media) and finishes not with a plan but with a set of covers (`JobResult::Covers`: found `ArtItem`s from the cache and reasons for the not found). The set is stored in `PlanStore` for up to an hour, like a plan.
  - `PlanImport` with `covers: <set id>` rebuilds the plan: after the game transaction comes the transaction writing `ART/<ID>_COV.png`; not-found ones go to "skipped"; duplicate IDs get one cover. A cover never blocks an import.
  - The UI starts the search after the first plan, shows the journal under the plan and disables "Confirm" while the plan is being rebuilt; cancelling the search leaves the plan without covers. The "Download covers for added games" checkbox is enabled by default and remembered (since ADR-0034 — "Download images", all source types, only on the add screen). In the CLI — `yaoplm add --covers` (network only with the flag, ADR-0007), with `--mirror` and `--skip-source`.
  - Titles from the database: `PlanImport.databaseTitles` gives the game a title from the built-in database (ADR-0024) if the ID is there, otherwise the title from the file name. The "Titles from the database" toggle on the add screen is enabled by default; in the CLI — `--db-titles`, off by default so that scripts get predictable names. A title different from the file name is noted in the plan.
- **Rejected.** Merging two plans on the client: the plan is the core's contract, the client does not edit it. Cover search inside `PlanImport`: the plan must be built in seconds and without network.
- **Consequences.** The "Download images" button in the library remains for games added earlier. A cover set older than an hour is rejected (`coversExpired`): the UI keeps the plan on screen, rebuilds it without covers and starts the search again.

## ADR-0032 — Art types: sources by type, cache keys, logo fits, variants to choose from
*2026-10-23, accepted in M5.* Refines SPEC ART-2, ART-3 and ADR-0025.
- **Context.** OPL reads eight image types (research/13 §1), and open sources do not exist for all of them. The sizes differ by type, and libretro logos come in any aspect ratio.
- **Decision.**
  - `ArtKind` and the protocol type `ArtType`: COV, ICO, COV2, BG, SCR, SCR2, LGO, LAB; sizes — `recommended_size` by profile (ICO 64×64 for OPL, 128×128 for RiptOPL).
  - Sources by type: xlenore — COV (flat cover, 3-D render `covers/3d/` as a second variant); libretro — COV (`Named_Boxarts`), SCR (`Named_Snaps`), SCR2 (`Named_Titles`), LGO (`Named_Logos`). For ICO, COV2, LAB and BG there is no open source: they come from art packs (ADR-0033) or manual replacement. `SourceEntry.kinds` tells the UI what a source has. *Superseded by ADR-0035: every type now has a network source (OPL Manager copy on archive.org, ScreenScraper with a key), and the source order is its own for each type.*
  - The libretro cache key contains the folder (`Named_Snaps/<name>`) except for `Named_Boxarts`, so that the M4 cache stays valid. Derived files are named `<TYPE>-<W>x<H>.png`.
  - Everything is stretched to the type size as OPL does, except LGO: the logo is fitted into the frame on a transparent background (`Fit::Contain`), otherwise the lettering is distorted.
  - `FindArt` is a job: all sources for one type of one game, already reduced images (PNG in base64) for choosing in the game card; the chosen variant is written by a regular `SetArt` plan. Mass download (`FetchArt.kinds`) takes the first found variant in source order.
  - The game card shows eight slots with a preview, size and the actions "Download", "Replace" (file, clipboard, drag-and-drop) and "Delete"; each action is a plan with a backup (ADR-0025).
- **Consequences.** In requests and journals the image type is an `ArtType` string; a client without the `kinds` field gets only COV. ICO 128×128 on standard OPL remains a question for a console check (research/13 §6).

## ADR-0033 — Art packs: only games on the Media, one pass, OPL Manager names and art.tar
*2026-10-23, accepted in M5.* Refines SPEC ART-5, ADR-0007 and ADR-0025.
- **Context.** Users have OPL Manager image backups (a zip of about 6 GB from archive.org, tens of thousands of games), folders with images and `art.tar` from RiptOPL and wOPL. The private OPL Manager server must not be touched (rule 3). Names in OPL Manager copies differ from OPL names: screenshots and backgrounds are numbered (`SCR_00`, `SCR_01`, `BG_00`), extensions are mixed (research/13 §3).
- **Decision.**
  - `ImportArt` is a job: it reads the selected packs (folders, .zip, .7z, .tar, individual images) once from start to end and takes **only images of games on the Media** (product owner's decision 2026-10-23); the rest are counted in the plan's notice. The job finishes with a plan: nothing is written before confirmation.
  - Names are parsed exactly (`yaoplm_formats::art::pack_picture`), case-insensitively and anywhere in the pack: `<ID>_<TYPE>.<extension>` and OPL Manager numbering (`SCR_00` → SCR, `SCR_01` → SCR2, `BG_00` → BG, other numbers are not used). If there are several files for one slot, png wins, then bmp, then jpg, then the rest.
  - Each image is re-encoded to PNG at the profile size, as when downloaded (ADR-0032), and goes through the `art-cache/local/` cache. An image larger than 16 MiB or unreadable is skipped with a reason. Images already on the Media remain unless the user asked to replace them; replaced ones go to `.yaoplm/backup/` (ADR-0025).
  - Reading: zip and 7z through `archive::for_each_file` (a solid 7z block is decoded once); tar — by our own lenient ustar reader (zero blocks skipped, GNU long names and pax, base-256 sizes), covered by a fuzz target. A folder is walked up to depth 8, hidden files are skipped, and only names resembling images are opened. On the server packs are selected inside the allowed roots (`PathPolicy`).
  - UI: "Import images" in the library (choosing packs, types and "Replace images already on the Media"), and the job journal names the pack and file of each image.
  - Read failures. In folders and zip each image is read on its own: an image that cannot be opened or decompressed (corrupt entry, unsupported compression method, encryption) and a folder that cannot be read are skipped with a path and reason, and the rest of the pack is taken. Irrelevant files (type not selected, game not on the Media, slot occupied) are not even opened. A tar and 7z stream cannot be read further after a decoding error, so such an error, like a pack that cannot be opened or a corrupt zip central directory, ends the job. CLI: `yaoplm art import <root> <packs>... [--kind T] [--replace]`.
- **Rejected.** Importing the whole pack: it would fill the USB stick with images of games not on it. Extracting the archive to a temporary folder: doubles space and time. Reading archives on archive.org through `view_archive.php`, as OPL PC Tools does: the user downloads the archive themselves. *Revised by ADR-0035 (product owner's decision 2026-10-24): YAOPLM reads the `OPLM_ART_2024_09` copy (an uncompressed zip) image by image via Range requests; the rejection remains in force for `view_archive.php` and solid 7z.*
- **Consequences.** Writing `art.tar` (for RiptOPL) remains for ART-6 in v0.3. Names from `PS2_LIST.CSV` in OPL Manager copies are not used: the built-in database provides them.
- **Refinement (2026-10-24, check against real copies).** The directory listings of `OPLM_ART_2024_09` and `OPLM_ART_2023_07` from archive.org confirmed the layout: all 196 745 names are parsed correctly (research/13 §3). Two corrections follow from the results: images from the pack's `PS1` folder are not taken (their IDs overlap with PS2 game IDs, and OPL looks for PS1 game images not by ID), and a PNG that is already the right size, no deeper than 8 bits and not interlaced is written to the Media as is — palette PNGs from the 2024 copies keep the palette instead of becoming RGB 2–2.6 times larger.

## ADR-0034 — Simple mode: what is hidden, the consistency rule, jobs without noise
*2026-10-24, accepted in M5.* Refines SPEC UI-4, UI-5, ART-8 and ADR-0030, ADR-0031.
- **Context.** The product owner found the interface overloaded: an ordinary user needs the game list, "Add games" and images, not sorting, counters, conversion and job journals. The USB scan appeared in jobs, sometimes twice in a row.
- **Decision.**
  - The `simpleMode` setting, enabled by default, the first item in settings. All screens read it through one hook `useSimpleMode()`; switching is instant, without a reload.
  - What is visible in simple mode is the table in SPEC §5.11. Everything hidden is available in expanded mode; in expanded mode the library's secondary actions (pack import, dump verification, conversion) are collected in the "More" menu.
  - The consistency rule: an element is hidden on all screens or on none. A property visible on the game card (disc type, format) can be filtered in the library; an action hidden in the library (conversion, dump verification) is hidden on the card too. Each rule is a table row and a check in `simpleMode.test.tsx`.
  - Hidden filters and sorting do not apply in simple mode but remain in the address and return together with expanded mode.
  - Plans are the same in both modes: this is the check before writing (rule 1 CLAUDE.md).
  - Jobs. The library scan is an internal action; in both modes it is absent from the jobs page and the floating panel: progress is visible in the library itself. The library request is observed on all screens, so changing the screen does not restart the scan; a scan nobody waits for is cancelled in the core too. In simple mode there is no jobs page: write progress is a floating panel with "Cancel", the result is a notification (`sonner`, MIT), and an error stays until dismissed. Line-by-line transaction steps in journals — only in expanded mode.
  - "Download images" in simple mode and "Download all images" in the game card — without a choice: all types that the enabled sources have, missing ones only, then a plan. When adding games the search also takes all such types (`FetchArt.kinds` together with `import`); the plan lists only the not-found covers, the other types are counted in the search result.
  - The link between the UI and the core (not with PS2 and not with the network) is shown only where it can be lost: in the browser. A closed event stream is not yet a loss (proxies close idle connections; the server sends a ping every 25 s): after 2 s the UI asks the core with a `Ping` request, and only if there is no answer does it show the banner. Everything behind the banner, and windows opened later, gets `inert` until the stream returns; after a real break the library and Media are read again. On the desktop the core is in the same process, so there is no indicator.
  - Hidden settings keep their values and apply (ID cross-check during scanning, image sources); if an action is impossible because of a hidden setting, the message says where to find it.
  - The add toggles ("Titles from the database", "Download images", "Verify dumps") live only on the add screen, where they are enabled by default and remembered; they are not in settings.
- **Rejected.** Separate screens for simple mode: the two interfaces would quickly diverge. Hiding warnings: they explain why OPL will not show a game. Hiding "Rescan", "N files OPL does not see", "Show all volumes", "File names" and the Redump DAT: without them the user will not refresh the list after edits in a file manager, will not understand where a game went, will not find the card in the built-in card reader and will not get a verification verdict (owner's decision 2026-10-24).
- **Consequences.** Every new UI element belongs to one of the modes and goes into the SPEC §5.11 table. E2e scenarios open expanded mode by default (`openLibrary`); the UI walkthrough (`walkthrough.spec.ts`) runs in both.

## ADR-0035 — A source for each art type: OPL Manager copy by Range, ScreenScraper by key, region policy
*2026-10-24, accepted in M5.* Refines SPEC ART-1, ART-2, ART-4, META-4, §5.4.1 and §7, ADR-0007, ADR-0025; replaces part of ADR-0032 on sources and revises the rejection in ADR-0033. Research — research/14.
- **Context.** The goal is to give every art type a working network source and to make the "download all images" button find everything the sources have. Sources without a licence cannot be bundled (ADR-0007) but may be queried at runtime. OPL Manager's private server must not be touched. A pack's images must be byte-exact with the game's cover of another region.
- **Decision.**
  - **OPL Manager copy** — source `oplm`, all eight types. The central catalogue (8.6 MB) is read once via Range requests and stored next to the image cache; then one Range request per image with a CRC-32 and size check against the catalogue. The program does not query a missing image (archive.org answers it with a 503 after 9 s); "not found" is given offline by the index. OPL Manager numbering: `SCR_00` → SCR, `SCR_01` → SCR2, `BG_00` → BG; without a background — `BG_01`+, then screenshots that OPL shows nowhere else (`SCR_02`+). One thread, a second between requests, retries on 5xx; if the `download` link does not answer, the element's servers from its metadata are used; after an index read failure the source rests for ten minutes. A file of a different size or a CRC mismatch — the index is deleted and read again. The mirror is a folder with the copy's layout (`PS2/<ID>/<ID>_<TYPE>.png`).
  - **ScreenScraper** — source `screenscraper`, all types: `box-2D`, `box-2D-back`, `box-2D-side`, `support-2D`, `ss`, `sstitle`, `fanart`, `wheel-hd`/`wheel`. Enabled only if the build or environment has a developer key (`YAOPLM_SCREENSCRAPER_DEVID`, `_DEVPASSWORD`, `_SOFTNAME`; in releases — from CI secrets, never into the repository); otherwise the source exists nowhere in the UI: neither in settings nor in the "About" source list (ADR-0034 consistency rule). The user does not enter their own developer key in the UI: that is registering the program, not the user. A user account is optional (settings or `YAOPLM_SCREENSCRAPER_USER`, `_PASSWORD`). One `jeuInfos.php` per serial number (`serialnum`, system 58), cache 30 days, "not found" — seven. Codes 401, 430, 431, 403, 423, 426 pause the source (ten minutes, six hours, until the end of the session). Credentials never reach the journal or the cache.
  - **Order by type** (`sources::order`): COV — xlenore, OPL Manager, libretro, ScreenScraper; ICO, COV2, LAB — OPL Manager, ScreenScraper; BG — OPL Manager, ScreenScraper, a libretro screenshot; SCR, SCR2, LGO — libretro, OPL Manager, ScreenScraper. A source whose images are smaller than the slot goes to the end: for RiptOPL (COV 280×400, ICO 128×128) the OPL Manager copy is last. The user does not choose the order; settings only have enabling, the mirror and the ScreenScraper account.
  - **Region policy** (`yaoplm_net::region`). Packaging (COV, COV2, LAB, ICO) — only by matching ID or serial number, by the Redump name with the game's region tag or by a ScreenScraper image with that region; an empty slot is better than a guess. A packaging image from the OPL Manager copy that matches byte for byte (CRC and size) an image of a game from another region group (NTSC-U, PAL, NTSC-J/K) is skipped in quiet downloads with the reason "only an edition from another region exists" (`notices.artOtherMarket`) and is offered last in the game card. Types shared across regions (SCR, SCR2, BG, LGO), if the game's own serial has nothing, are taken from other editions of the same game (the same Redump title without tags, up to two, US first): this is what RetroArch does with a short name.
  - `YAOPLM_OFFLINE=1` forbids any host except this computer; CI and the e2e server set it. Tests run on mirrors and a local Range server; real coverage is measured by a real-data test over the source file lists (research/14 §6).
- **Rejected.** Linking an image through `view_archive.php` without an index: each missing type costs 9 s and a 503 response. Re-uploading the copy to GitHub (Luden02): faster but without a licence — the owner's decision, not used for now. LaunchBox: no terms of use and no serial numbers, only with LaunchBox's permission. TheGamesDB: serial UIDs are wrong (DOA2). IGDB, MobyGames, GameTDB, SteamGridDB, IGN, Nostlan, the PSBBN database — research/14 §5. Generated LAB and ICO from a template (as in PSBBN): a made-up image instead of a found one; if they appear, disabled by default.
- **Consequences.** Coverage over 11 571 serials with a Redump name (research/14 §1): COV 92.4 %, SCR 83.4 %, BG 82.5 %, SCR2 75.9 %, LGO 73.6 %, COV2 56.6 %, ICO 52.7 %, LAB 52.1 %. The 98 % goal is not reached without ScreenScraper: Japanese and Korean editions have 25–32 % packaging, and there are no other open sources for it. The first image from the OPL Manager copy waits for the table of contents (37 s in a live check), then 0.4–1.6 s per image (archive.org can be slower, up to 5 s); the job shows progress and can be cancelled. If an archive.org item disappears, the source stops answering while the cache remains.

## ADR-0036 — Game settings and VMC: OPL menu rules, only changed values, cards are not overwritten
*2026-10-24, accepted in M5.* Refines SPEC CFG-1, CFG-2, CFG-5, VMC-1, §5.11.1, ADR-0019, ADR-0020, ADR-0021 and ADR-0034. Research — research/15.
- **Context.** The game settings editor must write what OPL will later read like its own and must not damage foreign data: common CFG databases have descriptions longer than 255 bytes, old 0.9.3 mode bits (`$Compatibility=100`), LF files; neighbouring managers lose keys (OPLNova), write `$GSMSource=0` which OPL treats as a "per-game" setting (OPL PC Tools), and create cards from zeros that OPL rejects (OrbitPS2). The OPL menu itself recreates a card of a different size without asking, and when leaving the VMC window it creates an 8 MiB card for every slot without a file.
- **Decision.**
  - **Writing rules — like "Save" in the OPL menu** (`guiGameSaveConfig()`, research/15 §1.1): the default value deletes the key; GSM, cheats and PADEMU "per game" while the `...Source` key exists (written as `1`), "globally" — when it is absent (the key is deleted, per-game values remain in the file, as in OPL); writing any setting except VMC slots adds `$ConfigSource=1` — so an update of the OPL compatibility list does not touch the user's settings. `$AltStartup` — uppercase, no longer than 21 characters and without `;1`: OPL builds `cdrom0:\<name>;1` into a 32-byte buffer.
  - **Only changed values are written.** The editor compares the settings with what is in the file now and touches only the differing ones; the other keys, lines, order, BOM and line endings remain byte for byte (CFG-1). Values that OPL would not understand are checked only for the changed settings: a strange `$AltStartup` or a long card name written by another program does not prevent changing a mode. The `$Compatibility` bits already in the file are preserved (old modes 7 and 8 from 0.9.3, RiptOPL bits from another USB stick); new bits must be known to the profile (0x01–0x20, up to 0x80 for RiptOPL). The UI shows only the profile's modes and mentions extra bits.
  - **`$DMA` is not shown in the editor and not written**: it only affects the internal HDD (and BDM over ATA in 1.2, where the level is ignored), and YAOPLM has no HDD yet (HDD-1). The key in the file is preserved and visible in the key list; bringing the field back goes together with HDD.
  - wOPL CFG (libconfig) is shown, but an edit plan is rejected with a reason (CFG-1).
  - **Plan.** One transaction per game: the `VMC/` folder and new cards, then a copy of the CFG to `.yaoplm/backup/<id>/` (CFG-5) and an atomic CFG write; this write is the commit point, and everything before it is rolled back. The transaction carries a "was → became" key list (`cfgChanges`); the plan shows it in both modes. Without changes the plan is not built (`settingsUnchanged`).
  - **The card is byte-for-byte like OPL's genvmc** (research/15 §2.1): a superblock with `MCDevInfo` fields, an indirect FAT in cluster 8, the FAT, a root directory with `.` and `..`, the rest 0xFF, no ECC, exactly 8, 16, 32 or 64 MiB; time — in Japanese, like the PS2 clock. Cross-checked against OPL's `pc/genvmc` (everything except time, byte for byte), against mymcplusplus (`check`, `df`, saving a save) and against genvmc cards from ps2vmc-tool (the superblock). The creation time is stored in the plan step, so recovery after a failure writes the same card.
  - **Writing the card** — a new `WriteVmc` step: a temporary `.yaoplm-part` file, space reserved before the first byte (ADR-0019), sync, rename. After the write Windows reports the file's fragment count (`FSCTL_GET_RETRIEVAL_POINTERS`); if there is more than one, the write result carries a `vmcFragmented` warning (`ExecutionReport.notices`), because OPL on BDM will not accept such a card. On Linux and macOS the count will come with whole-library fragmentation checking (IMP-7b).
  - **An existing card is not overwritten.** Creating a card with an occupied name is possible only with an explicit replacement request (`replace`, `--replace`, a checkbox in the UI); the old file, before the new one is written, is moved to `.yaoplm/backup/<id>/VMC/` together with its saves — there is no deletion, and a rollback returns it to its place (as with images in ADR-0025). YAOPLM still cannot delete or rename cards (ADR-0020).
  - **The default name is `<ID>_<slot>`**, as in OPL 1.1.0, plus `generic_0`/`generic_1`. We do not take the serial-group table from OPL 1.2's `src/vmc_groups.c`: the file has neither a licence header nor a note on where the data came from, and we do not port OPL code under AFL-3.0 (ADR-0002). The user can enter the group name themselves.
  - **Simple mode** (product owner's decision 2026-10-24): in the game card — compatibility modes 1–6 and a memory card for slot 1 (choose from `VMC/` or create one with the default name at 8 MiB). Slot 2, card size and name, GSM, cheats, PADEMU, `$AltStartup`, CFG path and key list — only in expanded mode. Settings are an editor, not a game property, so there is no filter for them in the library (the ADR-0034 consistency rule concerns properties and actions).
  - CLI: `yaoplm cfg <root> <game>` shows, and with `--mode`, `--no-mode`, `--vmc`, `--alt-startup`, `--set`, `--unset` plans an edit; `yaoplm vmc ls` and `yaoplm vmc create … [--game G --slot 0|1] [--replace]`.
- **Rejected.** Rewriting the CFG entirely, like OPL's `configWrite()`: comments are lost and long values are truncated to 255 bytes. Writing `$...Source=0` for "globally": OPL reads that as a per-game setting. Deleting the old card with delete confirmation: saves would be lost forever, while moving to a backup folder only costs space. A zero or "sparse" file instead of a formatted card. Sizes larger than 64 MiB (OPL PC Tools): the OPL menu does not create them.
- **Consequences.** OPL sees settings written by YAOPLM as "User" (`$ConfigSource=1`). Replacing a card leaves up to 64 MiB per card in `.yaoplm/backup/`. Counting card fragments is so far available only on Windows. The RiptOPL profile writes 0 modes by deleting the key, like OPL; the explicit `$Compatibility=0` with which RiptOPL disables its default modes, and its extra keys, are a task for the RiptOPL profile (ART-6, M6).

## ADR-0037 — Fragmentation check: count from the OS, profile rule, warning after write
*2026-10-24, accepted in M5.* Refines SPEC IMP-7b, LIB-4, §5.11.1, ADR-0019 and ADR-0036. Research — research/06 §1.11.
- **Context.** When starting a game, OPL on BDM (USB, MX4SIO, iLink, BDM HDD) asks the driver for the fragments of each file and puts them into one table of 64 records (`BDM_MAX_FRAGS`). Upstream compares the limit with each part separately, so a game that exceeds it only in total does not get a clear refusal. OPL 1.1.0 requires every game file to be one fragment, and a VMC to be one fragment on any build. No neighbouring manager counts fragments: TinyPS2Manager warns by the number of files on the Media, the rest are silent.
- **Decision.**
  - **The count comes from the OS, without reading the FAT from the device.** Windows — `FSCTL_GET_RETRIEVAL_POINTERS`, without administrator rights. Linux — `FS_IOC_FIEMAP`, and if the filesystem does not support it, `FIBMAP` once per cluster. The vfat and exfat drivers have no FIEMAP at all, and the kernel answers FIBMAP only to a process with `CAP_SYS_RAWIO`, so without root on FAT32 and exFAT the count is unknown. macOS — `fcntl(F_LOG2PHYS_EXT)`. Adjacent extents that continue each other on the device are one fragment. A "cannot do it" error becomes an explicit "unknown" (`Fragments::Unknown`), not "all good" and not a warning.
  - **`unsafe` is in three modules** instead of one (refinement ADR-0019): `sys/windows.rs`, `sys/fiemap.rs` (ioctl through `rustix::ioctl`) and `sys/log2phys.rs` (`fcntl` through the `libc` crate, macOS only). Rust allocates the ioctl structures, and each block has a `SAFETY` comment. `libc` (MIT/Apache-2.0, the rust-lang team) was already in the dependency tree; `rustix` has no arbitrary `fcntl`.
  - **The rule comes from the profile** (`LoaderProfile::fragment_limit`): 1.2.0 beta and RiptOPL — no more than 64 fragments per game in total across all parts; 1.1.0 — each file in one fragment. The check runs only on local FAT32 and exFAT: SMB, MMCE and NTFS folders have no limit.
  - **Library** (LIB-4): after scanning the API counts the fragments of each game and of the VMC from its CFG. A game over the limit gets a `gameFragmented` or `gameFragmentedOpl110` warning; a card in a slot — `vmcSlotFragmented`; they are visible in the game card and go into the "Only games with warnings" filter. The fragment count is shown in the card details (expanded mode only), in the `PIECES` column of `yaoplm scan` and in the `Pieces:` line of `yaoplm info`.
  - **After writing** (product owner's decision 2026-10-24): the executor counts the fragments of the game that an import or conversion transaction has just written and, if the limit is exceeded, puts the same warning with advice into the result. There is no warning in the plan before writing: the fragment count is known only after writing, and indirect signs (little free space, already fragmented games) give false alarms. The plan remembers the profile it was built for (`Plan.profile`, in the journal — `opl-1.2`, `opl-1.1`, `riptopl`), so that recovery checks by the same rule.
  - **Advice — as in the OPL README:** copy the games to a computer, format the Media and add them again. We do not recommend defragmenters (the OPL README explicitly advises against them), so the word "defragment" was removed from the `vmcFragmented` text. YAOPLM itself defragments nothing.
- **Rejected.** Our own FAT32/exFAT parsing from the block device: on Linux it needs access to `/dev/sdX` (the `disk` group or a udisks password), on Windows administrator rights, and the gain is only Linux without root. Product owner's decision 2026-10-24: "unknown" for now. A warning in the plan — see above. Defragmentation by YAOPLM itself.
- **Consequences.** On Linux without root on FAT32 and exFAT, "unknown" is shown instead of a number. On macOS 15 too: the FAT32 and exFAT drivers in user space do not answer `F_LOG2PHYS_EXT` (CI `real-fs-macos`, 2026-10-24); the code remains — if Apple adds an answer, the numbers appear by themselves. CI `real-fs` checks both cases (without root and as root via `sudo -E`); the `real-fs-macos` job — mounted `hdiutil` images. Neutrino (NHDDL, the Neutrino launcher in RiptOPL) shares the same 64 records between the image and both VMCs; that rule will come with the profiles of those loaders.

## ADR-0038 — Beginner path, build and version selection, build replacement
*2026-10-24, accepted by product owner's decision.* Refines ADR-0013, ADR-0022 and ADR-0034; details — SPEC UI-6 (§5.11.2), LDR-6 (§5.10.2), LDR-7 (§5.10.3), findings — research/07 §1.11.
- **Context.** The owner wants the program to guide a complete beginner: insert a USB stick and be told what to do next, in simple mode, which is enabled by default. The installation wizard needs a conscious build choice (official OPL 1.1.0 and 1.2.0 beta, YAOPL, RiptOPL) with version, date, size and changelog, a choice of a specific version and replacement of one build with another without losing games. Repositories store releases differently: upstream overwrites `latest` in place and of the 1.x releases keeps only `v1.0.0` and `v1.1.0`, YAOPL publishes only the `master` tip, RiptOPL — only rebuildable variants.
- **Decision.**
  - The beginner's next step is computed by the core from what it already knows (`InspectDevice`, scanning, journals), without network: an enum value in the response, texts — in the UI in English. The order of states is fixed (SPEC §5.11.2). Hints exist in both modes, in expanded mode as one line.
  - Removable Media with a "Not suitable for OPL" verdict that formatting would fix (wrong filesystem or partition layout) gets "Prepare Media…" — the DEV-4 wizard with mandatory formatting and all ADR-0013 protections. It still has no install, update or replace buttons (ADR-0022). Media that cannot be fixed (system, read-only, sector not 512 bytes) gets only an explanation.
  - The preparation wizard chooses the filesystem itself by launch method and build (research/06). On "Don't know" — FAT32: all OPL builds and all launch methods read it, and large games go to `ul`.
  - Build descriptions and the "Recommended" mark are catalogue data (`summary` in English, `recommended`), not translation files: the catalogue is updated without a program release. The catalogue test checks that the English text is present.
  - Version selection — only from the build repository's GitHub releases, filtered by the catalogue by profile presence (§4 SPEC): for upstream these are `latest` and `v1.1.0`. Earlier 1.2.0 betas are not stored on GitHub and are not selectable. The OPL build archive on MEGA that the README links to is not a download source: it needs its own MEGA client, and ADR-0014 requires official releases; the user installs such a build from their own archive (LDR-2). RiptOPL is chosen by variants (catalogue channels), not by versions. The YAOPL fork's CI will publish every build as an immutable release with a version tag next to `latest` (a task in the fork repository). Version selection — only in expanded mode: a beginner needs the latest channel build.
  - Build replacement — one plan: conversions first, then folders, the loader last. Games, covers, CFG, VMC and cheats are not touched; global loader settings are neither moved nor deleted. Before confirmation the plan checks the library against the new build's profile and lists what will stop working, with a suggestion to fix it (ZSO → ISO, JPG and BMP → PNG). On OPL 1.1.0 on exFAT we do not switch by a regular replacement: only an explanation and the path through preparing the Media again.
  - The release text is foreign data: we show the beginning as plain text, no more than 10 bullet points, links only to github.com.
- **Rejected.** Hints the UI outputs itself without a step from the core: the web and CLI would diverge. Downloading old OPL betas from MEGA. Keeping copies of old OPL builds ourselves (ADR-0014: we do not distribute binaries). Version selection in simple mode.
- **Consequences.** The catalogue gains `summary`, `recommended` fields and a channel version selection rule; the API — the beginner-path step in `InspectDevice` and a "What will change for games" section in the replacement plan. A task is needed in the YAOPLM repository: versioned releases and an edit to `FORK.md`. RiptOPL in descriptions and replacement — together with forks in M6. Which build to recommend to a beginner is decided by the owner (SPEC, open question 7).

## ADR-0039 — Automatic profile detection: signs by strength, Media key, "Auto" by default
*2026-10-24, accepted in M5.* Refines SPEC LIB-1, §5.1.1, ADR-0004 and ADR-0023. Research — research/16 (signs of OPL versions and forks), research/07 §1.9.
- **Context.** ADR-0023 decided that the profile is determined by the Media, and the setting sets the default and the override. There is no loader catalogue, install manifest or hash history yet (LDR-1…LDR-4), the ELFs are packed with ps2-packer, and OPL 1.1.0 and 1.2 share the name `OPNPS2LD.ELF`. The study of signs (research/16) showed that some rules in SPEC §5.1.1 are inaccurate: `mmce_*` keys are written by YAOPL too; 1.2 keys in `conf_opl.cfg` survive a rollback to 1.1.0, and stronger than them is the absence of keys that every beta since build 1871 writes; `games.bin` by record size tells which OPL generation last listed the folder; a single `nhddl/` folder is not yet NHDDL.
- **Decision.**
  - **Signs by levels** (core, `yaoplm_core::detect`); the first level where the signs agree decides:
    1. an ELF whose SHA-256 is in `data/loader-hashes/opl-stable.txt` (all 34 ELFs from the official v1.0.0 and v1.1.0 archives, computed by YAOPLM 2026-10-24: GitHub does not provide hashes for these releases) — "exact", 1.1.0 rules;
    2. files of one family: RiptOPL `title.cfg` with `Version=`, `settings_riptopl.cfg`, `conf_riptopl.cfg`, `config.path`, `favourites.bin` (`OFAV`), `ART/art_cache.bin` (`ARC\0`); `wopl_*.cfg`, `conf_wopl.cfg`, `conf_uopl.cfg`; `nhddl/cache.bin` (`NIDC`), `nhddl/lastTitle.bin`;
    3. `CD/games.bin`, `DVD/games.bin`: records of 92 bytes — OPL 1.1.0 or a beta before build 2016; 188 bytes — a beta since build 2017 or a fork;
    4. `conf_opl.cfg`: keys that 1.2 always writes (`bdm_cache`, `enable_bgm`, `x_sensitivity`, `enable_bdm_hdd` and neighbours, `mmce_*`) — 1.2; OPL keys without them — 1.1.0 rules;
    5. ELF names: `RIPTOPL*`, `WOPNPS2LD*`, `nhddl*`, `OPNPS2LD*`, `OPL.ELF`.
  - exFAT and ZSO exclude 1.1.0 for levels 3–5 and, without other signs, give 1.2.0 beta. A stronger 1.1.0 sign on such Media remains: that the Media does not suit OPL 1.1.0 is stated by Media advice (DEV-2) and the notice about invisible ZSOs.
  - Signs of the same level that disagree (for example, two different loaders by name) decide nothing: detection goes lower, and the card shows a "several loaders" notice. A `games.bin` of a different generation than the chosen loader is also a notice: the console may be launching another OPL copy (from a memory card).
  - Without signs — OPL 1.2.0 beta ("default"); JPG covers then add a hint (betas since build 2169 do not load them), but do not change the profile.
  - wOPL, uOPL, NHDDL, the MMCE fork and YAOPL get 1.2.0 beta rules until they have their own profiles.
  - **What applies** (API, `ActiveProfile`): the Media override, then the explicit profile in settings, then detection. `ListDevices` and `InspectDevice` responses carry the profile, source, reason (a core phrase), found loaders and notices; Media advice is computed for the effective profile.
  - **The override key** is `serial:<volume serial number>` for USB and SD (the USB stick keeps the choice under another drive letter), `path:<root>` for folders and network folders. Overrides are stored in the UI settings (the desktop and the browser have their own, like other settings); nothing is written to the Media.
  - **The setting** (*replaced by ADR-0040: the setting no longer exists*) "Loader profile": "Auto (by Media)" by default. An old saved OPL 1.2.0 beta setting (it was saved on any settings edit) becomes "Auto"; deliberately chosen OPL 1.1.0 and RiptOPL remain.
  - **UI:** the line "Loader: profile — reason" with a "Change" menu (profile for this Media or "Auto") on the Media card and in the library header, in both modes. Library scanning waits for the Media response so as not to scan a 1.1.0 USB stick by 1.2 rules.
  - **CLI:** `--profile auto` by default; `yaoplm device` and `yaoplm scan` print the profile and reason, `yaoplm device` also the found loaders.
- **Rejected.** Storing the override on the Media (`.yaoplm/profile.json`): that is a write the user did not ask for (product owner's decision 2026-10-24). A sign from a single `nhddl/` or `POPS/` folder: they are created both by PSBBN installers and by managers. Reading the version from a packed ELF: the version string is visible only in unpacked VARIANTS — that is LDR-4's task. *Refinement ADR-0041:* the version string is read from a packed release ELF too (it contains a regular LZMA stream) and has become a detection level.
- **Consequences.** On a USB stick from which OPL does not start (OPL on a memory card), the profile is almost always "default" until the console leaves a `games.bin`; YAOPLM deletes `games.bin` after its own writes (IMP-8), so the sign appears again only after a view on the console. The signs are a snapshot of the code as of 2026-10-24; YAOPL and the forks change quickly, so before changing the rules they must be checked against the current code (research/16 §13).

## ADR-0040 — Profile only by Media: no global setting; the manifest is checked by hash
*2026-10-25, accepted by product owner's decision.* Refines SPEC LIB-1, §5.1.1, LDR-4, §5.10.1, ADR-0023 and ADR-0039.
- **Context.** After ADR-0039 the "Loader profile" setting had two meanings: "Auto" (by Media) and an explicit profile that **suppressed** detection on all Media. Product owner (2026-10-25): every Media has its own loader, the user often does not know its version, and a global choice that overrides what is on the Media only confuses; for exceptions there is a choice on the Media card. At the same time — about the future install manifest (LDR-3): the user can replace OPL themselves, and the manifest will describe the old build.
- **Decision.**
  - **There is no global profile setting.** The choice for Media on its card applies (key — volume serial number or path, ADR-0039), otherwise detection by the Media files (levels in SPEC §5.1.1), otherwise OPL 1.2.0 beta.
  - Previously saved `loaderProfile` and `profile` are ignored when reading settings; overrides for Media remain.
  - API: the `profile` field in `ListDevices` and `InspectDevice` remains for the CLI (`--profile` sets the profile for one run); the UI does not pass it. The source `setting` was renamed to `explicit`.
  - **The manifest itself decides nothing.** During recognition (LDR-4) YAOPLM computes the SHA-256 of the found ELF and compares it with the manifest:
    - it matches — the build is exactly the one recorded in the manifest;
    - it does not match — the ELF was replaced without YAOPLM: the actual files decide (hash history, `title.cfg`, names, signs in §5.1.1), and the Media card shows that the manifest is outdated;
    - there is no ELF at the manifest's path — the same, the manifest is outdated.
    The manifest is not rewritten by itself; the next install or update through YAOPLM will update it.
- **Rejected.**
  - A global profile as a fallback for "no signs": it confuses just the same, while one choice on the card solves it for a specific Media forever.
  - Moving the old explicit profile into overrides: it is unknown which Media it referred to.
  - A manifest as an independent sign above the hash: it describes the past, not what is on the Media.
- **Consequences.**
  - Anyone who chose OPL 1.1.0 or RiptOPL in settings gets the Media profile after the update; where there are no signs, the profile is chosen on the card once.
  - On a USB stick without signs (OPL starts from a memory card, the console has not left a `games.bin` yet) the profile is "default" with a clear reason on the card and in the library header, not a hidden setting.

## ADR-0041 — Version inside the loader ELF; the profile question for prepared Media without signs
*2026-10-25, accepted by product owner's decision.* Refines SPEC LIB-1, §5.1.1, LDR-4, ADR-0039 and ADR-0040. Research — research/16 §1.6, §9–§13.
- **Context.** The version string was considered unavailable: release ELFs are packed with ps2-packer. A check on 2026-10-25 showed that they contain a regular LZMA stream: a ps2-packer header of six numbers, a properties byte, a dictionary, the data and an end marker one byte before the size from the header. The product owner asked to build this version into detection and to reconcile it with the other signs, including where settings files are left over from a previous fork, the installation is crooked or there are no signs at all. If there are no signs, the user must choose the version themselves, and "don't know" should give 1.1.0 rules. Empty Media gets no question: a loader is installed on it first.
- **Decision.**
  - `yaoplm_formats::ps2_elf` reads the version string: in plain text in unpacked ELFs, after LZMA decompression — in packed ones. The string is searched for as a separate C string or after `/` (`RiptOPL/v…`, `User-Agent`: in RiptOPL builds with RetroAchievements there is no other copy). Decompression is limited to 32 MiB (the whole EE memory), nothing is executed; a damaged or truncated file gives "version unknown", not an error and not a wrong version.
  - Detection levels (SPEC §5.1.1):
    1. the checksum and the version inside the ELF together — "exact"; two ELFs that disagree at this level (OPL 1.1.0 in `UPDT/` and a beta in `APPS/`) decide nothing;
    2. files of one family;
    3. `games.bin`;
    4. `conf_opl.cfg`;
    5. ELF names.
  - The version gives the rules: 1.0, 1.1 and upstream betas before build 1871 — 1.1.0 rules; a fork suffix (`-yaopl`) cancels the number ladder.
  - The ELF family is taken from the program's own strings (`settings_riptopl.cfg`, `conf_riptopl.cfg` — RiptOPL; `wopl_settings.cfg`, `conf_wopl.cfg` — wOPL; `conf_uopl.cfg` — uOPL; `conf_opl.cfg` — OPL), not from the file name, so a renamed ELF is recognised. RiptOPL's `title.cfg` yields to the version inside the ELF.
  - New notices: files of another loader next to the one whose ELF decided (`leftoverLoaderFiles`, "probably leftovers of a previous installation"); a file with a loader name that is not a PS2 program (`loaderNotPs2Elf`).
  - OPL 0.5–0.9.3 are not packed with LZMA: their 25 ELFs are appended to `data/loader-hashes/opl-stable.txt` and recognised by checksum with 1.1.0 rules.
  - The `InspectDevice` and `ListDevices` response carries `detected.library`: the root has OPL folders (except a single `APPS/`) or `ul.cfg`.
  - **The question "Which OPL do you launch from this Media?"** is a line on the Media card and in the library, not a window. It is shown only if the profile is taken by default (no signs), `library` is true and the Media doctor (DEV-2) does not consider the Media unsuitable for OPL: on a system drive, an NTFS USB stick and the like the version question means nothing. The answers — OPL 1.2 or YAOPL, OPL 1.1.0, RiptOPL, "Don't know (rules for any OPL)" — are saved as the choice for the Media. "Don't know" is stored as `unknown` and sent to the core as OPL 1.1.0 rules; the loader line explains this. If later the Media files say something different from the choice, "By the Media files this is …" is shown with a "Return to 'Auto'" button.
- **Rejected.**
  - A window when Media is connected: a USB stick without signs is a normal case (OPL on a memory card), a window on every connection gets in the way.
  - A question for empty or foreign Media: it needs a loader installation (beginner path, SPEC §5.11.2), and that decides the profile.
  - A "Later" button that silently keeps 1.2 rules.
  - UCL decompression for OPL 0.x instead of the hash table: the builds are frozen, the hashes suffice.
- **Consequences.**
  - A check on real builds (research/16 §1.6, §13; `scripts/loader-corpus.py`, the `loader_elfs` and `loader_corpus` tests with `--ignored`): 451 ELFs from 98 release assets give exactly the version that follows from the release names and git history; 1 649 damaged copies never gave a wrong version; 1 207 installation combinations on 303 loaders are detected correctly.
  - Every detection reads the loader ELF in full (up to 64 MiB) and decompresses it, about 4 MB per Media. The `ps2_elf` fuzz target was added to the weekly run.
  - The signs are a snapshot of the build code as of 2026-10-25: before changing the rules they must be checked against the current code (research/16 §13).

## ADR-0042 — Loader installer: catalogue as data without hash history, presets, languages, startup settings and a foreign ELF
*2026-10-25, accepted by product owner's decisions (answers to questions before LDR-1…LDR-7 in M5).* Refines ADR-0014, ADR-0022, ADR-0038 and ADR-0041; findings — research/17.
- **Context.** Before implementing the installer (SPEC LDR-1…LDR-7, BOOT-1) we had to decide where to put the ELF by default, what to do on MX4SIO, whether to install language packs and startup settings, and how to handle a foreign ELF at the install location. Neighbouring tools (research/17) overwrite the ELF without a backup, do not write a manifest and do not detect the version; the FreeMcBoot installer puts OPL 1.0.0 on the card, and all five standard `FREEMCB.CNF` (1.953, 1.963–1.966) try `mass:/UPDT/OPL.ELF` first. ADR-0022 assumed keeping a hash history of every floating-channel build; with ADR-0041 the version is read from the ELF itself, and the product owner asked whether a history is needed at all then.
- **Decision.**
  - **Catalogue.** `data/loaders/index.toml` (build order and `schema`) and one file per build: `opl-stable` (tag `v1.1.0`), `opl-beta` (`latest`), `yaopl` (`latest`). Parsing is strict: an unknown field is an error, a new field bumps `schema`; a program that does not know the schema of a fresh catalogue stays on its own copy. The copy is embedded in the program (`yaoplm_core::loaders`); a fresh one from `main` passes the same checks. Tests check that the `summary` and `limits` texts exist in English (`web/src/locales/*`) and follow the typography of `docs/I18N.md`.
  - **There is no hash history of new builds** (product owner's decision 2026-10-25). The build on the Media is recognised by the version string inside the ELF (ADR-0041): on releases it matched the release names and git history for 451 ELFs, and for the three downloaded for the catalogue (1.1.0, the `latest` beta, YAOPL) too. The catalogue channel by version is set by `fingerprints.versions` and `fingerprints.suffix`: `v1.1.0` — `opl-stable`, `v1.2.0-Beta-…` without a suffix — `opl-beta`, `…-yaopl` — `yaopl`. The `data/loader-hashes/opl-stable.txt` table (ADR-0041) remains only for frozen releases whose version cannot be read (0.5–0.9.3), and for 1.0.0 and 1.1.0; no new rows are added to it. The hash is also needed in two more places: to verify the downloaded file and to confirm our installation (manifest, ADR-0040).
  - **Download confirmation.** Each channel has its own hash sources: the GitHub `digest`, the release's `SHA256SUMS` file, hashes pinned in the catalogue. The hash the user saw before confirmation is pinned in the plan and checked after download; the file is accepted only if all sources that know it agree. GitHub does not provide hashes for 1.1.0, so the archives `OPNPS2LD-v1.1.0.7z` and `OPNPS2LD-LANGUAGES-AND-FONTS-v1.1.0.7z` are pinned in the catalogue with hashes computed by YAOPLM 2026-10-25; the release is frozen and they do not change.
  - **"Newer".** Within one channel — by the build number from the version string; the number of the channel's fresh build is taken from the release (asset name, release name, tag) on "Check for updates" and cached. The date is the asset's `updated_at`, the commit is the tag link, not `published_at` and `target_commitish`. The same number with a different commit is a different build, not an update: numbers from different forks are not compared.
  - **"Recommended"** — OPL 1.2.0 beta (SPEC, open question 7 closed).
  - **Presets.** On a USB stick by default — FreeMcBoot: `UPDT/OPL.ELF`. PS2BBL: `APPS/OPNPS2LD.ELF`. The OPL application: `APPS/OPL/OPNPS2LD.ELF` with `title.cfg` (`title=Open PS2 Loader`), for YAOPL — `APPS/YAOPL/` (`title=YAOPL`). The answer "Don't know" to the launch-method question puts the ELF in both standard paths (`UPDT/OPL.ELF` and `APPS/OPNPS2LD.ELF`). A separate FMCB 1.953 preset `OPL.ELF` is not needed: `UPDT/` exists in 1.953 too.
  - **MX4SIO.** The wizard asks where the Media will work: a USB stick or an SD card in MX4SIO; the default is by bus (through a USB card reader an SD card looks like USB). FreeMcBoot does not launch from MX4SIO, and no launcher has a standard path, so for MX4SIO — the application preset or a custom path, the BOOT-1 lines for PS2BBL-MX4SIO (`massX:/…`) and OSDMenu (`mx4sio:/…`), and the "OPL on a memory card" option (folders only, no ELF). `APPS/OPNPS2LD.ELF` for MX4SIO — only after a console check: PS2BBL will find it there only with a certain device order.
  - **A foreign ELF at the install location.** An OPL that YAOPLM recognises (manifest, version inside the ELF or "OPL, version unknown" by name) is replaced, and the previous file goes to `.yaoplm/backup/loader/` by the same plan; the plan shows the size and SHA-256 of the replaced file. A file of another family or an unrecognised one — only with the "Replace this file" mark in the plan, and a backup is made then too. There is no deletion.
  - **Backups** — the last three per path; older ones are deleted by the same plan and are visible in it.
  - **Language packs** — optional, disabled by default: "OPL menu language" with a language choice. Only the chosen language and its font are installed, flat in `LNG/`; the files are searched for by the names `lang_<Language>.lng` and `font_<Language>.ttf|otf` at any depth of the archive and in one nested zip (betas have a zip inside a 7z, 1.1.0 has folders). The manifest remembers the pack, and "Update" updates it together with the ELF: the language file is tied to the version.
  - **Startup settings** — only in expanded mode, via a checkbox. OPL reads `conf_opl.cfg` from the Media only if there is none on the memory card, and then it enables USB in "auto" mode itself and afterwards saves settings to the Media (`src/opl.c`, `checkLoadConfigBDM` and `trySaveAlternateDevice`, in `b3a2199` and `v1.1.0`). Therefore: if there is no file — we write `usb_mode=2` (and `language_text` if a language is chosen); if there is a file — we change only these keys, the rest and their order are preserved; we warn that with settings on the card the file will not work. For MX4SIO we do not write: OPL will not see the file until MX4SIO is enabled.
  - **`LICENSE` and `CREDITS`** are not copied to the Media (betas and YAOPL have them only inside the 7z); the licence, authors and links are shown in the install window.
  - Build variants (`PADEMU`, `IGS`, `RTL`, `-nosio2man`) are not offered in v0.2. A fresh catalogue is taken from `main` (raw.githubusercontent.com) on "Check for updates"; the daily check is disabled by default.
- **Rejected.**
  - A hash history of every floating-channel build (a daily workflow would append `digest` and `SHA256SUMS` to `data/loader-hashes/`, and the fork's CI — `HASHES.txt`): the version inside the ELF recognises any build, including betas from the MEGA archive and RiptOPL variants rebuilt several times a day, while the history would grow every day, become stale in the embedded copy and still miss builds replaced within a day.
  - Overwriting without a backup and "update when the hash is different" (this is what neighbours do, research/17 §9 e, g). Copying `LICENSE` and `CREDITS` to the Media. Startup settings by default and for MX4SIO. The FMCB 1.953 preset at the root.
- **Consequences.**
  - The core gains a `loaders` module (catalogue, version strings and their order, channel by version), the API — `LoaderCatalog`, the CLI — `yaoplm loader ls`.
  - It is impossible to distinguish "a file from the official release byte for byte" from "built from the same commit"; this does not affect the profile or the update offer.
  - If upstream changes the packer, new builds will be "version unknown" until ELF reading is updated (ADR-0041); tests on the release corpus (`loader_elfs`) will show this on the first new release.
  - Until the first "Check for updates" the program without network knows nothing about builds newer than those that existed when it was released; the "Update available" window works from the cache after the first check.
  - The `HASHES.txt` task in the YAOPLM fork's CI is cancelled; YAOPLM versioned releases (ADR-0038) are still needed for version selection and rollback without a backup.

## ADR-0043 — Downloading loader builds: jobs, verification by hash and version, ELF storage, catalogue from `main`
*2026-10-25, accepted in M5 (LDR-2).* Refines ADR-0014, ADR-0022 and ADR-0042.
- **Context.** LDR-2 requires downloading builds only from official releases and only on a user action, holding the download to the SHA-256 the user saw, showing the licence and the start of the changelog before download, installing from one's own file without network and pulling a fresh catalogue from `main`. The core is synchronous (ADR-0003), and the network lives in `yaoplm-net`.
- **Decision.**
  - **Jobs.** Network — only in jobs started by the user: `LoaderRelease` (what will be downloaded: version, date, file, size, SHA-256 and what confirms it, licence, links to the release and commit, up to ten changelog points), `DownloadLoader` and `UpdateLoaderCatalog`. `ImportLoader` reads the user's file without network, `LoaderFiles` lists what is stored.
  - **Where from.** The release description — `GET /repos/<repo>/releases/tags/<tag>` with the `ETag` of the previous response (a 304 response does not consume GitHub's 60 requests per hour limit); files — only from `https://github.com/<repo>/releases/download/`, a link to another host or a foreign repository in the release description is rejected; the catalogue — `raw.githubusercontent.com/belomaxorka/yaoplm/main/data/loaders/`. A mirror folder with the same layout replaces the network in tests, CI (`YAOPLM_OFFLINE=1`) and without internet.
  - **The download holds to what the user saw.** The `DownloadLoader` request carries the SHA-256 from `LoaderRelease`: if the floating tag was rebuilt in the meantime, the download is rejected ("rebuilt, look at the new build"). The downloaded file is checked against the release size, against SHA-256 (all sources that know it agree) and then against the version inside the ELF (ADR-0041): it must match the release version if readable. A file that fails the check is not stored.
  - **Storage.** `<data>/loaders/elf/<sha256>.elf` and next to it a `.json`: version, build, tag, release file and archive member, SHA-256 of the release file, source, whether the hash was confirmed, time. The same release file is not downloaded a second time. Release descriptions with `ETag` — in `loaders/releases/`, the catalogue from `main` — in `loaders/catalog/`. Records are written to a temporary file with `fsync` and rename.
  - **Without network** "Release details" show the last saved response with a mark; download needs network.
  - **Own file.** An ELF or a zip/7z with exactly one loader ELF (by the catalogue's `fingerprints.elf`; in an archive with several — a request to extract the needed one). Family — by the program strings, version — from inside the ELF, channel — by the catalogue. Only a file whose SHA-256 is in the frozen-release table (`opl-stable.txt`) is "confirmed"; the rest are shown as "your file, nobody vouches for it".
  - **The catalogue from `main`** is saved only if it is read by the same parser and checks as the embedded one and its schema is known to the program; otherwise the previous one remains. A saved catalogue applies only to the program version that read it: a new program carries an embedded copy no older than that.
  - **The changelog** is plain text: HTML is stripped, links remain only to github.com (the commit or PR before the author's profile), service lines (checksums, "Automatic … build", "Full Changelog") are dropped, no more than ten points of 200 characters.
- **Rejected.** Downloading the language pack together with the build: it is needed only when installing with a chosen language (LDR-3). A GitHub token for the request limit: `ETag` and the cache suffice. Following links from the release description to any host: a substituted description must not redirect the download.
- **Consequences.** The core gets `loaders::{release, notes, download, local}`, the network — `yaoplm_net::loaders` (`ReleaseSource`, `LoaderNet`, `LoaderStore`), the API — the requests and jobs above, the CLI — `yaoplm loader release|download|import|files|update-catalog`. The ELF storage does not clean itself: a build weighs about 1.4 MB; cleaning will come with installation backups if needed.

## ADR-0044 — Loader installation: one plan, backups, foreign file, launch strings
*2026-10-25, accepted in M5 (LDR-3, BOOT-1).* Refines ADR-0021, ADR-0040, ADR-0042 and ADR-0043.
- **Context.** ADR-0042 decided where to install the ELF and what to do with a foreign file; ADR-0043 — how to download a build. What remained was how the install plan itself is structured, how it rolls back, what the user sees before and after writing, and how it looks in the UI and CLI.
- **Decision.**
  - **Plan.** `PlanInstallLoader` builds one plan from the ELF storage (ADR-0043); the request carries the SHA-256 of the file downloaded for the shown hash. Transactions in order: build folders (LIB-3) → one per ELF path → language pack → manifest → startup settings. A path transaction: missing folders, the previous file is renamed to a backup, the new ELF is written to a temporary `.yaoplm-part` with `fsync` and rename (the commit point); after it, copies older than three are deleted; for the application preset the same step writes `title.cfg` (`title`, `boot`, foreign keys and their order preserved). A failure at any step before the commit rolls the path back entirely: the previous ELF returns to its place.
  - **Backups** — `.yaoplm/backup/loader/<UTC YYYYMMDD-HHMMSS>/<path with _ instead of />` (`APPS_OPNPS2LD.ELF`); three are kept per path, the new one among them. Deleting old ones is visible in the plan as "old backup of the replaced loader" and does not require a user-file deletion mark: these are our copies.
  - **What lies at the path** is decided by YAOPLM by the file itself, not by the name: the same SHA-256 — nothing is done ("this exact build is already there"); a program of the same family (strings inside the ELF, ADR-0041) — replacement with a copy; another program or an unreadable file — the plan error `loaderForeignFile` with the size and SHA-256, until the user marks "Replace this file" (then it is a transaction warning, and a copy is made the same way); a folder in place of the file — an error.
  - **Forbidden paths.** The path must be relative, inside the Media and end in `.ELF`; `.yaoplm/` and the service files of the memory card emulator's SD (`.sd2psx`, `MemoryCards`, `PS1`, `PS2`, `mcp2.bin`, `os`, case-insensitive) are rejected.
  - **The manifest** `.yaoplm/manifest.json`, `schema` 1: one record per path (build, tag, version, SHA-256, path, preset, `usb`/`mx4sio`, language, source, time). An unreadable manifest or one newer than the schema is replaced, and the plan checks before writing that the file remained the one that was read.
  - **The language pack** is downloaded only when a language is chosen (`DownloadLoader` with `languages`) and stored next to the ELF (`loaders/langs/<sha256>`); only files of the chosen language go into `LNG/`.
  - **"OPL already on the memory card"** does not install the ELF: the wizard builds a regular folder plan (`PlanInit`).
  - **Launch strings (BOOT-1)** are computed by the core by the preset's launchers and the Media (`LoaderBootHints`): the standard config launches the path — "no need to configure"; otherwise — lines for `FREEMCB.CNF` and `OSDMENU.CNF` (`name_OSDSYS_ITEM_N`, `path1_OSDSYS_ITEM_N`) or `PS2BBL.INI` (`LK_AUTO_E1`), `mass:` for USB, `massX:` and `mx4sio:` for MX4SIO; for the application — a name on the "Applications" page. YAOPLM does not write launcher configs. After the lines — a reminder to enable the device in the OPL settings.
  - **UI.** The "Install loader…" button is on the Media card where the loader can work (not the system drive, not read-only, verdict not "Not suitable for OPL", §5.10.1). Wizard: where the Media will work (default by bus) → how OPL is launched (build presets, "Don't know", "OPL already on the memory card", in expanded mode "Custom path") → which build (the recommended one is selected) → release details (version, date, size, licence, links, changelog; SHA-256 in expanded mode) → optionally the menu language in the UI language and, in expanded mode and only for USB, startup settings. Release details are requested by a `LoaderRelease` job when the wizard opens (one per build, cache 10 minutes). The "Replace this file" mark — in the plan window, next to the buttons: it rebuilds the plan. The release mirror is an expanded-mode setting.
  - **CLI:** `yaoplm loader install <root> <build> [--preset P]... [--path PATH] [--mx4sio] [--language NAME] [--starter-settings] [--replace-foreign] [--file FILE | --tag T --mirror DIR]`: download with confirmation, plan with confirmation, then the launch strings.
- **Rejected.** Deleting the previous ELF or keeping one copy per Media: a rollback must return exactly the file that was at the path. Deciding "foreign or ours" by the file name: `OPNPS2LD.ELF` can be both wLaunchELF and RiptOPL. Writing lines into `FREEMCB.CNF` or `PS2BBL.INI` on the memory card (BOOT-1: a foreign config can break the launch). Downloading release details only on a button: the user must see the licence and changelog before downloading.
- **Consequences.** The core gains `loaders::{install, boot, languages, manifest}`, `PlanKind::InstallLoader` and `Removal::Backup`; the API — `PlanInstallLoader`, `LoaderBootHints`, `LoaderLanguages`; the `make_library` fixture — the release mirror `mirror/loaders` and an empty `stick` root. LDR-4 relies on the manifest and backups ("Roll back"), LDR-7 — on the same plan with a different set of transactions first.

## ADR-0045 — Loader update and rollback: what is installed, cache instead of network, "Not now"
*2026-10-25, accepted in M5 (LDR-4).* Refines ADR-0040, ADR-0042, ADR-0043 and ADR-0044.
- **Context.** SPEC §5.10.1 requires the Media card to know the installed build and its channel, to offer "Update to …" only within the channel, to show the "Update available" window without network access, to remember "Not now" and to allow rolling back an update. Detection (ADR-0041) already reads the version inside the ELF, the manifest (ADR-0044) is written by installation, and backups are made by the same plan.
- **Decision.**
  - **What is installed** (`yaoplm_core::loaders::installed`). Every loader found by detection plus manifest records at paths detection does not look at (the user's custom path). The catalogue build and where it is known from, by strength: manifest — only while its SHA-256 equals the file; frozen-release hash; version inside the ELF (channel by catalogue templates); name only — then only the family is known. If the manifest has a different hash, the file was replaced without YAOPLM: the file itself decides, and the card says "Replaced without YAOPLM". For each path — the last backup and its version.
  - **"Newer"** — `BuildVersion::channel_order` (ADR-0042): the same release, a higher build number; another fork suffix or the same number with a different commit is not ordered, and it is not considered an update.
  - **Cache instead of network.** The latest channel version is taken from the saved GitHub release response (`loaders/releases/`, the file time — the check time; a 304 response updates it). A mirror response is saved the same way as the GitHub response: the mirror replaces the network entirely. The device list (`ListDevices`, `InspectDevice`) reads the catalogue and these responses once per request and returns in `DeviceInfo.installed` the version, the last known version, the check time, `freshness` (`current`, `update`, `unknown`) and the backup. The "Update available" window gets release details with a `CachedLoaderRelease` request — also without network.
  - **"Check for updates"** on the card reads the catalogue from `main` (its error does not stop the check) and the release of the installed build's channel. There are no other network accesses: the window appears only after a check or download the user has performed.
  - **The "Update available" window** opens by itself on the Media screen once per "Media key (`serial:<volume serial number>` or `path:<root>`), SHA-256 of the installed ELF" pair. Any closing, including "Not now" and a completed update, remembers the pair in settings (`loaderUpdatesOffered`, the last 100). The "Automatically offer loader updates" setting (enabled by default) disables the window entirely; the "Update to …" and "Check for updates" buttons on the card remain. Only for Media where the loader can work (§5.10.1).
  - **Update** (`PlanUpdateLoader {root, path, sha256}`) — the same plan as installation, with `update`: no folders, no `title.cfg`, no startup settings; only the ELF at the installed path is replaced (the previous one goes to a backup), plus the language pack if the manifest remembers it, and the manifest. The saved ELF must be of the same build as the installed one (`loaderFileOtherBuild` otherwise): changing the channel is "Replace…" (LDR-7). The window shows the installed and the new version, date, size, changelog, release links, commit and "What changed since your version" (a commit comparison on GitHub when both are known).
  - **Rollback** (`PlanRollbackLoader {root, path}`) swaps the current ELF and the last backup: the current one goes into a new copies folder (with a `-1` suffix if the second matches), the copy returns to the path, and the emptied folder is deleted. A repeated rollback cancels the first. The manifest follows the file: a catalogue build — a record with its version, the source — the copy file; another program (for example, a restored wLaunchELF) — the record is deleted. The language pack is not rolled back: there is one pack per Media in `LNG/`.
  - **"Reinstall…"** on a card with an installed build opens the installation wizard (ADR-0044) with that build and its preset. "Replace…" with a breakdown of what will change for games — LDR-7.
  - **CLI:** `yaoplm loader update <root> [--path P] [--mirror DIR] [--yes|--dry-run]` (reads the release, says "already latest" or asks about the download and builds a plan), `yaoplm loader rollback <root> [--path P]`; `yaoplm device` prints an `Installed:` line with the build, state and backup.
- **Rejected.** Checking for updates when the screen opens or on a default timer: network only on a user action (ADR-0007); the daily check remains disabled as a future setting. Remembering "Not now" by the new build version: the "Media, installed ELF" pair does not resurface after every new beta, but after an update or rollback — a new pair. Rollback "by manifest history": the backup is the only reliable copy of the previous file.
- **Consequences.** The core gets `loaders::{installed, rollback}`, `PlanKind::{UpdateLoader, RollbackLoader}`, and `FoundLoader` — SHA-256; the API — `DeviceInfo.installed`, `PlanUpdateLoader`, `PlanRollbackLoader`, `CachedLoaderRelease`; the fixture — the `mirror/loaders-next` mirror with beta 2280. Before the first check the card knows nothing about new builds: it shows neither "Up to date" nor "Update to …", and the CLI writes "not checked for updates".

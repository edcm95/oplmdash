# YAOPLM — testing

## Fixtures

- **We never commit real games to the repository.** Fixtures are generated by code in `yaoplm-test-support` (its own ISO9660 generator, ADR-0016; ready-made `SYSTEM.CNF` variants — `Variant`):
  - a tiny ISO9660 with `SYSTEM.CNF` (`BOOT2 = cdrom0:\SLUS_200.62;1`) and an empty ELF;
  - variants without `BOOT2`, with different case, with a long ID;
  - BIN/CUE (raw 2352-byte sectors) from the same ISO;
  - ZSO from the same ISO;
  - a mini-DAT in Logiqx format;
  - a FAT32 image a few MB in size (`FatImage`, via `fatfs`);
  - `VirtualFile`/`VirtualIso`: a 4.5 GiB stream generated on the fly for slicing tests; `VirtualSources` substitutes such files as import sources;
  - `MemFs`: an in-memory device with FAT semantics (case-insensitive names, 4 GiB − 1 limit, free space), large files stored as 16-byte "samples" every MiB, `unplug_after(n)` simulates a pulled stick, `fail_once` — one failed operation;
  - `bincue`: BIN/CUE in all four sector modes (MODE1/2048, MODE1/2352, MODE2/2336, MODE2/2352), with and without a track gap.
- Golden files live in the repository as small binary files. In `.gitattributes` they are marked `binary` so CRLF in CFG is not corrupted.

## Cross-checks

- **ZSO:** `ziso.py` from the OPL repository unpacks our files (`align` 0 and 2), and we read its files (`-c 1` and `-c 9`). The test `crates/yaoplm-formats/tests/opl_oracles.rs`, in CI — the `oracles` job.
- **`USBA_crc32`:** two kinds of test vectors.
  1. Real "game name → CRC" pairs from `ul.XXXXXXXX.*` chunk names on a stick prepared by OPL Manager or USBUtil (the owner sends the file list; the games themselves are not needed). There are none yet; there are 4 vectors from ulmake's tests (research/08 §4).
  2. Values from the C function in OPL's `src/system.c`, compiled into a test harness on 5000+ random names. `cc` is a dev dependency only. OPL code (AFL) does not enter the repository: the test takes it from a clone (`YAOPLM_OPL_SRC`), and CI downloads the files at a pinned commit.
- **`ul.cfg`:** comparison with a `ul.cfg` created by OPL Manager (sent by the owner).
- **CFG:** round-trip of 40,860 real CFG files from community databases (Tom-Bruise, VTSTech) without changes, plus editing one key does not touch the others (`tests/corpus.rs`, needs `YAOPLM_TESTDATA`). The settings editor (CFG-2) on the same files and on 70 GDX-X CFG files: without edits the file does not change by a single byte, switching a mode touches only `$Compatibility` and `$ConfigSource`, old 0.9.3 bits remain.
- **VMC:** an empty 8/16/32/64 MiB card matches byte-for-byte (except the timestamp in the root) the card from OPL's `pc/genvmc`, built from the clone (`opl_oracles.rs`, in CI — the `oracles` job); mymcplusplus checks our cards (`check`, `df`, `ls`) and writes a save directory into them; the superblocks of genvmc cards from ps2vmc-tool (`samples/oplcard.bin`, `card16mb.bin`, `card32mb.bin`, not committed) match ours (`vmc_oracles.rs`, needs `YAOPLM_TESTDATA`).
- **File fragments:** `crates/yaoplm-device/tests/fragments.rs` counts the pieces of real files read-only (`YAOPLM_FRAGMENT_FILES`), to cross-check with `fsutil file queryextents`. On the owner's stick (FAT32) ul parts and `ul.cfg` are one piece each, as with `fsutil` (repeated 2026-10-24: five GTA SA parts, one piece each). The same file has `fragments_on_real_drivers`: on a mounted FAT32/exFAT image it writes a file in one pass (one piece) and two files alternately one cluster at a time (many pieces); `YAOPLM_FRAGMENTS_KNOWN=1` or `0` requires the OS to report or not report. CI: the `real-fs` job runs it without root (`0`) and under root via `sudo -E` (`1`: a file in one pass — 1 piece, alternating — 16 each), the `real-fs-macos` job — on `hdiutil` images (macOS 15 does not yet report the layout for either FAT32 or exFAT; the test accepts both outcomes and prints it). OPL rules and warnings are checked by `crates/yaoplm-core/tests/fragments.rs` on `MemFs::set_fragments`.
- **CHT:** parsing of 3,629 OPL-Widescreen-Cheats files (`tests/corpus.rs`).

- **Loader profile (LIB-1):** signs and their order — unit tests in `crates/yaoplm-core/src/detect.rs` on `MemFs` (checksum with a substitute table, family files, `games.bin` of both generations, `conf_opl.cfg` keys, exFAT/ZSO, conflicting loaders); override, explicit `--profile` and device key — `the_loader_profile_of_a_device` in `crates/yaoplm-api/tests/plans.rs`; CLI output — `devices_and_device_doctor`; interface — `web/tests/e2e/loader.spec.ts` (places `settings_riptopl.cfg` in the fixture for the duration of the test) and `web/tests/unit/settings.test.ts` (the old global setting no longer works, ADR-0040). The OPL 1.0.0/1.1.0 hash table was checked against a real ELF from the official archive (`D:\yaoplm-testdata\downloads\opl-v1.1.0\`). The version inside an ELF — unit tests in `crates/yaoplm-formats/src/ps2_elf.rs` (packed and unpacked ELF, truncated and corrupted copies); on real builds — `loader_elfs` (451 ELF files from 98 OPL release assets, forks, NHDDL and Neutrino; versions are checked against the list from release names and git history; for each release folder — corrupted copies: truncation, headers, LZMA properties, stream bytes) and `loader_corpus` (detection on the same ELF files: a clean install, a renamed ELF, leftovers of another fork, a cut-off file, two ELF files of different generations). The sample is collected by `scripts/loader-corpus.py`, only in `D:\yaoplm-testdata\downloads\loaders`. Fuzz target `ps2_elf`.

- **Loader downloads (LDR-2, ADR-0043):** unit tests in `crates/yaoplm-core/src/loaders/{release,notes,download,local}.rs` (the download offer for each catalogue build, agreement of `digest` and `SHA256SUMS`, the pinned 1.1.0 archive, files not from project releases, the changelog from release texts, checking size, hash and version inside the ELF, a custom ELF and archive); `crates/yaoplm-net/src/loaders.rs` on a mirror and on a local HTTP server (`ETag` and 304, external links rejected, storage); `crates/yaoplm-api/tests/loaders.rs` and `loader_release_download_import_and_files` in `apps/cli/tests/cli.rs` on the `yaoplm_test_support::loaders::ReleaseMirror` mirror with test ELF files (no network: the substituted 1.1.0 archive is rejected, a rebuilt tag is rejected, the catalogue from the mirror's "main" is saved and rejected).

## Failures and recovery

`crates/yaoplm-core/tests/recovery.rs` (ADR-0021):
- the stick is "pulled out" in the middle of the third chunk of a 4.4 GB game → journal rollback leaves no `ul.*`, and completing leaves five correct chunks and `ul.cfg`;
- an interrupted recovery starts again and runs to completion;
- cancel rolls back only the current game; a failure writing `ul.cfg` deletes the already written chunks;
- a failure after the commit point (deleting `games.bin`) is completed even if "rollback" is chosen.

An exFAT image cannot be tested locally: there is no Rust library that writes files to exFAT (`exfat-fs` 0.1 only reads and formats). exFAT logic is covered by `MemFs`, and the real driver by the CI `real-fs` job on Linux.

## Fuzz and property tests

- `crates/yaoplm-formats/tests/properties.rs` (proptest, in the normal `cargo test`): CFG without losses, `set` does not touch foreign keys, `ul.cfg` and ZSO round-trip, parsers do not crash on garbage.
- `fuzz/` (cargo-fuzz, nightly): targets `iso`, `system_cnf`, `cfg`, `ul_cfg`, `zso`, `cht`, `tar` with the same invariants. In CI once a week (`fuzz.yml`), in normal CI only a build check. The `iso` target starts from the fixture corpus (`write_fixtures`).

`cargo run -p yaoplm-test-support --example make_boot_iso -- --elf <ELF> --out <ISO> [--min-mib 4300]` builds a bootable image from an open homebrew ELF (ID `YAOP_000.01`). Nothing real: all images and pictures are generated. `--games 3000` — for testing virtualization.
2. Preview via `.claude/launch.json`: `yaoplm-server-fixture` (7878; `web/tests/e2e/server.mjs` builds the fixture in a temporary folder and starts the server with three roots), `yaoplm-server-fixture-3000` (the same with 3000+ games, for virtualization) plus `web-dev` (Vite, 5173, proxies `/api`). ## Test data outside the repository

The `D:\yaoplm-testdata\` directory (more space on D:; not in git):
```
D:\yaoplm-testdata\
├─ iso\         # the owner's own dumps (not downloaded by the agent)
├─ homebrew\    # free homebrew ELF/ISO for tests
├─ opl\         # official OPL builds from GitHub releases (1.1.0 and 1.2.0 beta), for reference
├─ loaders\     # files of official releases for manual installer checks (LDR-1…LDR-7): <build>-<tag>\<asset>, downloaded with the owner's permission
├─ images\      # FAT32/exFAT images for integration tests
├─ refs\        # clones of reference repositories (ADR-0015, research/REFERENCES.md)
└─ out\         # run results
```
Tests that need real data are marked `#[ignore]` and run only when `YAOPLM_TESTDATA=D:\yaoplm-testdata` is set.

Picture names from OPL Manager backups (ART-5): `oplm-art\<item>.tsv` — tables of contents of the archive.org copies, written by `python scripts/oplm-backup-toc.py D:\yaoplm-testdata\oplm-art OPLM_ART_2024_09 OPLM_ART_2023_07` (only the zip's central directory, about 8 MB per copy, without pictures). Test: `cargo test -p yaoplm-formats --test oplm_backups -- --ignored --nocapture`.

Picture source coverage (ART-1, ADR-0035): `art-lists\` — xlenore and libretro file lists, written by `python scripts/art-source-lists.py D:\yaoplm-testdata\art-lists` (five requests, without pictures), and the table of contents `oplm-art\OPLM_ART_2024_09.tsv`. The test `cargo test -p yaoplm-api --test art_coverage -- --ignored --nocapture` prints a coverage table by type and region using the same code that selects sources (research/14 §1, §6).

Live picture source check (manually, before a release or when a source behaves strangely, not in CI): `YAOPLM_LIVE=1 cargo test -p yaoplm-net --test live -- --ignored --nocapture` — the table of contents of the OPL Manager copy and all DOA2 types in three regions from archive.org, xlenore, libretro, ScreenScraper with a key.

Network in tests: all tests run on mirrors and local servers; CI and the e2e server set `YAOPLM_OFFLINE=1`, and the HTTP client refuses any host except this computer, so a test that forgot a mirror fails instead of going to the internet.

**The agent does not download commercial game images**, even small ones. Allowed downloads: official OPL releases, open tools (`ziso.py`, hdl-dump and similar from sources), homebrew, open databases. To test on the console without commercial games, we build our own test ISO from an open homebrew ELF with `SYSTEM.CNF`; with a filler file the same ISO also tests `ul` slicing (> 4 GiB).

### Sessions with the owner's devices (agreement 2026-10-24)

The product owner will connect sticks and the memory-card emulator's microSD ("PSX Memory Card"), which comes from the factory with FreeMcBoot and OPL, and later everything else from the table above. The goal is to teach YAOPLM to recognise different device layouts and work with what is already on them, and to verify this on the console. Procedure:
1. **Read-only inventory.** For each device: partition table, FS, cluster, volume serial, folder tree, loader files (ELF, `title.cfg`, settings files) and the emulator's service files. Record the factory layout of the emulator's microSD before any changes: it is the reference for LDR-1, LDR-3 and LDR-4 (MMCE). The result goes to `docs/research/` (file lists, sizes, hashes; the ELF files themselves, card images and firmware do not enter the repository) and, where needed, into test fixtures.
2. **Writing — only via a plan.** Installing different OPL builds (OPL 1.1.0, 1.2.0 beta, YAOPL, RiptOPL) on sticks and swapping one build for another (LDR-3, LDR-4) — through YAOPLM plans, with the owner's confirmation and a re-check of the serial number before each write. The emulator's service files (`.sd2psx/`, `MemoryCards/`, `PS1/`, `PS2/`, `mcp2.bin`, `os/` and whatever the inventory finds) are never touched.
3. **Console testing** per the matrix below; results and notes go to `docs/testing/`.

## What is needed from the owner

1. A PS2 with OPL 1.2.0 beta (the latest build). Preferably also OPL 1.1.0, on a second stick or selectable at launch.
2. Sticks: one FAT32, one exFAT, at least 8 GB. One stick can be reformatted between checks.
3. The model and firmware version of the memory-card emulator; the size and FS of the SD cards in the emulator and in MX4SIO (the agent can inspect them read-only).
4. Dumps of **your own** discs in `D:\yaoplm-testdata\iso\`:
   - a CD game (blue side of the disc);
   - a DVD game up to 4 GiB;
   - a game larger than 4 GiB (DVD-9 or a large DVD-5);
   - later a PS1 game in BIN/CUE and, if available, a multi-track one.
5. If possible, a stick prepared by OPL Manager: the file list and `ul.cfg` are needed for reference values. If there is none, the `USBA_crc32` reference comes from OPL's C function compiled in the test.
6. Later: a network adapter for SMB and an HDD for the internal drive (fat PS2).
